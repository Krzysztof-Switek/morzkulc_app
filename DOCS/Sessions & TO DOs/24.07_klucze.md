## 1. Kluczowe odkrycie — połowa danych już istnieje

Sprawdziłem dokładnie kod syncu (`functions/src/service/tasks/usersSyncFieldsFromSheet.ts`) i arkusz na żywo. **Kolumna „Klucze do siedziby" jest już od dawna synchronizowana** do Firestore:

- Arkusz „CZŁONKOWIE I SYMPATYCY", kolumna **„Klucze do siedziby"** (już istnieje, TAK/NIE) →
- zsynchronizowana do `users_active/{uid}.admin.hasClubKeys` (boolean) przy **każdym** przebiegu `users.syncFieldsFromSheet` (wymagana kolumna, sync padnie bez niej — więc gwarancja, że dane są świeże).

Czyli backend do „fizycznych kluczy" **nie wymaga żadnej zmiany w syncu** — tylko odczytu tego, co już jest w Firestore. Reszta pracy to: nowa kolumna „Dostęp akademik" (opcjonalnie synchronizowana tym samym mechanizmem), nowy endpoint zwracający listę, i nowy moduł frontendowy.

## 2. Stan modułu „Klub" w APP_SETUP — już częściowo przygotowany

Sprawdziłem arkusz APP_SETUP na żywo — **modul_9 jest już przemianowany na „Klub"** z dokładnie taką konfiguracją dostępu, jaką opisałeś:

```
Id_elementu:        modul_9
Nazwa_wyświetlana:  Klub
Aktywny:            FALSE   ← do zmiany na TRUE (ostatni krok wdrożenia)
Kolejność:          9

Dostep_czlonek:     TRUE
Dostep_kandydat:    TRUE
Dostep_sympatyk:    FALSE
```

To dokładnie pokrywa się z Twoim „wszyscy kandydaci i członkowie" (+ zarząd/KR, bo to też pełni członkowie). Nic tu nie trzeba zmieniać poza samym `Aktywny` — zrobimy to na końcu, po wdrożeniu kodu, żeby moduł nie pojawił się pusty/błędny w międzyczasie.

**Wymagana zmiana w kodzie:** `resolveModuleType()` w `public/core/modules_registry.js` obecnie rozpoznaje etykiety `sprzęt/godzinki/imprezy/basen/ranking/zarząd/kurs/kurs_godzinki` — brakuje mapowania `"klub"` → nowy typ modułu. Bez tego moduł „Klub" wyrenderowałby się jako generyczny stub („Moduł w budowie") — dokładnie ten sam problem, który mieliśmy z „Raporty zarządu".

## 3. Nowa kolumna w arkuszu — „Dostęp akademik"

**To Ty dodajesz kolumnę w arkuszu** (nie ja — to Twoja tabela źródłowa, zachowujesz pełną kontrolę nad formatowaniem/pozycją). Wymagania, żeby sync ją podchwycił:

- Zakładka: **CZŁONKOWIE I SYMPATYCY** (ta sama, gdzie jest „Klucze do siedziby").
- Nazwa nagłówka: **„Dostęp akademik"** (dokładnie ta, którą podałeś — normalizacja nagłówków w kodzie poradzi sobie z wielkością liter/spacjami/polskimi znakami, więc „Dostęp akademik", „dostęp_akademik" itp. zadziała identycznie).
- Wartości: **TAK / NIE** (albo puste = NIE) — tak samo jak przy „Klucze do siedziby".
- Pozycja w arkuszu: dowolna, kod czyta po nazwie nagłówka, nie po numerze kolumny.

**Kolumna jest OPCJONALNA dla syncu** — dokładnie na wzorze istniejącej kolumny „opiekun stażu": jeśli jej jeszcze nie dodasz, reszta syncu (w tym „Klucze do siedziby") działa jak dotychczas bez błędu. Gdy ją dodasz — sync automatycznie zacznie ją odczytywać, bez potrzeby ponownego deployu backendu (kod będzie już gotowy na jej pojawienie się, patrz sekcja 4).

## 4. Zmiany w kodzie — backend

### 4.1 `functions/src/service/tasks/usersSyncFieldsFromSheet.ts`
Dodać opcjonalną obsługę nowej kolumny, wzorem istniejącego „opiekun stażu" (linie ok. 245-247):
```ts
if ("dostep_akademik" in hmap) {
  candidates.push(["admin.hasAkademikAccess", normalizeBoolish(g(row, "dostep_akademik"))]);
}
```
Nazwa pola Firestore: **`admin.hasAkademikAccess`** (boolean) — symetrycznie do istniejącego `admin.hasClubKeys`.

### 4.2 `functions/src/api/getKlubInfoHandler.ts`
Rozszerzyć o listę osób z kluczami/dostępem, widoczną **tylko** dla ról z dostępem do modułu Klub (kandydat/członek/zarząd/KR — czyli `memberRoleKeys`, dokładnie ta sama grupa co w arkuszu). Dopisać do `GetKlubInfoDeps` pole `memberRoleKeys: string[]` (już istnieje w `service_config.ts`, trzeba tylko przekazać w `index.ts`).

Logika:
```ts
const canSeeKeys = memberRoleKeys.includes(roleKey);
if (canSeeKeys) {
  const [withKeysSnap, withAkademikSnap] = await Promise.all([
    db.collection("users_active").where("admin.hasClubKeys", "==", true).get(),
    db.collection("users_active").where("admin.hasAkademikAccess", "==", true).get(),
  ]);
  // scal po uid → { name, hasClubKeys, hasAkademikAccess }, sortuj alfabetycznie po nazwisku
}
```
Dodać `klucze: [...]` do odpowiedzi JSON tylko gdy `canSeeKeys` (analogicznie do `finanse.stanKonta`, które dziś już gatuje się tak samo dla zarządu/KR — ten sam sprawdzony wzorzec w tym samym pliku).

**Ważne — dlaczego NIE dodawać tego bezwarunkowo:** `/api/klub` jest dziś wołany przez box „Klub" w profilu, widoczny dla WSZYSTKICH zalogowanych (w tym sympatyk/kursant). Gdyby lista kluczy trafiała do odpowiedzi zawsze, sympatyk/kursant zobaczyliby ją przez samo wywołanie sieciowe, mimo że frontend by jej nie pokazywał — real security-relevant leak, którego unikamy tym samym sprawdzonym wzorcem co przy finansach.

### 4.3 `index.ts` / `firebase.json`
Brak nowych endpointów — `getKlubInfo` już istnieje i jest wdrożony. Trzeba tylko dopisać `memberRoleKeys` do wywołania `handleGetKlubInfo(req, res, {..., memberRoleKeys: svcCfg.memberRoleKeys})` w eksporcie funkcji.

### 5.3 `public/core/render_shell.js` — kafelek na stronie głównej
Wzorem kafelka „Zarząd" (widoczny tylko gdy user ma dostęp), NIE wzorem „Basen" (zawsze widoczny, disabled) — bo dostęp do Klubu jest rolowo ograniczony (bez sympatyka/kursanta), więc kafelek powinien być **całkowicie ukryty**, a nie wyszarzony, dla ról bez dostępu.
```js
const klubModule = (ctx.modules || []).find((m) => m?.type === "klub");
const canSeeKlub = klubModule ? canSeeModule({ ctx, module: klubModule }) : false;
```
Dodać kafelek `data-home-action="klub"` w gridzie kafelków (obok „Zarząd"), z handlerem analogicznym do `admin-pending`:
```js
if (canSeeKlub) {
  const klubBtn = viewEl.querySelector("[data-home-action='klub']");
  klubBtn?.addEventListener("click", () => setHash(klubModule.id, "klucze"));
}
```
Wymaga importu `canSeeModule` z `/core/access_control.js` (już zaimportowany w `render_shell.js` — używany w `renderNav`/`renderView`, więc tylko trzeba go użyć też w `renderHomeDashboard`).
