# Kalendarz rezerwacji sprzętu (kajaki + pozostałe kategorie)

Data: 2026-09-03
Status: **plan zatwierdzony, wdrożenie w toku (tryb auto)**

## Kontekst

Dziś rezerwacja sprzętu (`public/modules/gear_module.js`, modal `#gearBundleModal`) polega
na dwóch niezależnych natywnych polach `<input type="date">` ("Data od" / "Data do").
Nic nie pokazuje użytkownikowi, które dni są już zajęte — dowiaduje się o konflikcie
dopiero po kliknięciu "Zapisz rezerwację", z ogólnego komunikatu błędu z backendu
(`code: "conflict"`). Ten sam problem dotyczy edycji terminu w "Moje rezerwacje"
(`public/modules/my_reservations_module.js`).

Celem jest zastąpienie tego kalendarzem miesięcznym: zajęte dni widoczne od razu
(pomarańczowo-bursztynowa obwódka + ikonka kłódki), klik dnia startu i dnia końca
podświetla wybrany zakres na zielono, dopiero wtedy aktywny staje się przycisk
"Zapisz rezerwację". Wzorzec wizualny (siatka miesiąca, kolorowe obwódki dni, ikony,
nawigacja miesiącami) już istnieje w aplikacji — kalendarz basenowy na stronie głównej
(`renderHomeBasenCalendar`, `public/core/render_shell.js:1091-1241`) i kalendarz admina
basenu (`renderCalendarShellHtml`, `public/modules/basen_module.js:780-823`) — ale
dokładna kombinacja "zajęte=pomarańczowe+kłódka, zakres=zielony, wybór klik-klik" nie
istnieje jeszcze nigdzie w kodzie i trzeba ją złożyć z tych klocków + nowej logiki
wyboru zakresu.

**Ustalony zakres (przez pytania do użytkownika):**
1. Kalendarz obejmuje **wszystkie kategorie sprzętu** dostępne w modalu (kajaki, wiosła,
   kapoki, kaski, sprayskirty, rzutki), nie tylko kajaki.
2. Kalendarz zastępuje pola dat **też przy edycji terminu** istniejącej rezerwacji
   (lista "Moje rezerwacje" + dedykowany widok edycji), nie tylko przy tworzeniu nowej.

**Świadomie poza zakresem:** limity horyzontu (`*_max_time`) i maks. długości
(`max_reservation_length`) nie są dziś eksponowane na frontend — kalendarz nie będzie
wyszarzał dni poza tymi limitami, backend nadal je waliduje przy zapisie i błąd wyświetla
się jak dziś (`mapUserFacingApiError`). To nie regresja, tylko świadome ograniczenie
zakresu tej zmiany (chodzi o widoczność zajętości, nie o te dwa osobne limity).

## Architektura rozwiązania

### Nowy współdzielony komponent: `public/core/date_range_calendar.js`

Zarówno modal tworzenia rezerwacji (`gear_module.js`), jak i dwa miejsca edycji terminu
(`my_reservations_module.js`) potrzebują identycznego zachowania — zamiast duplikować
~200 linii logiki siatki miesiąca + maszyny stanu wyboru zakresu w dwóch plikach (co jest
uzasadnione tylko dla jednolinijkowych helperów jak `todayIso()`, nie dla komponentu tej
wielkości), wydzielamy go do `public/core/`. To zgodne z istniejącą konwencją — moduły
już importują z `core/` (np. `apiGetJson`/`apiPostJson`), zasada "core nie importuje z
modules" jest jednokierunkowa i tu nie ma zastosowania.

Czysta funkcja/fabryka, bez zależności od domeny sprzętu — przyjmuje dane, zwraca
HTML string + bindowanie zdarzeń (ten sam styl co `renderCalendarShellHtml` w
`basen_module.js`: plain DOM, template literals, `innerHTML =`, żadnego frameworka —
lekkie na mobile):

```js
export function createReservationCalendar({
  containerEl,          // element do wyrenderowania kalendarza
  todayIso,              // dzisiejsza data (lokalna, nie UTC)
  occupiedRanges,        // [{ startIso, endIso, label }] — blockStartIso/blockEndIso + userDisplayName
  onRangeChange,         // (startIso|null, endIso|null) => void — wywoływane po każdej zmianie
}) { ... return { setOccupiedRanges(ranges), reset(), destroy() }; }
```

**Stany dnia w siatce** (analogicznie do `basenCalDay--*` w `basen.css:479-565`, nowe
klasy `gearCalDay--*`):
- `--blank` — dopełnienie przed 1. dniem miesiąca.
- `--past` — przed dziś, wyszarzone, nieklikalne.
- `--occupied` — dzień mieści się w `[blockStartIso, blockEndIso]` którejś aktywnej
  rezerwacji tego przedmiotu → **obwódka `#f59e0b`** (ten sam odcień co istniejący
  `.basenCalDay--kursowy`, wizualnie pomarańczowo-bursztynowy) + ikonka kłódki
  (przeniesiona/re-użyta `lockIconSvg()` z `gear_module.js:2270-2272`, dziś używana
  tylko jako mały badge przy karcie kajaka, `gear_module.js:1742`). Klik nieaktywny do
  wyboru zakresu, ale pokazuje krótką podpowiedź inline pod kalendarzem: "12–15 lipca —
  zajęte (Jan Kowalski)" (z `userDisplayName` zwracanego już dziś przez backend) —
  odtwarza informacyjną wartość usuwanej sekcji tekstowej, wzorem `showDayPreview` w
  `render_shell.js:1142-1161`.
- `--available` — wolny dzień w przyszłości, klikalny.
- `--start` / `--end` / `--in-range` — **zielone** (`#22c55e`, jak `.basenCalDay--mine`)
  po wybraniu zakresu.

**Maszyna stanu wyboru** (lokalny stan w zamknięciu, jak `state.year/month` w
`renderCalendarTab`, `basen_module.js:921`):
1. Brak wyboru → klik wolnego dnia D → `rangeStart = rangeEnd = D` (pojedynczy zielony
   dzień).
2. Wybrany jeden dzień → klik innego wolnego dnia D2:
   - D2 == rangeStart → odznacz (reset).
   - inaczej: `newStart/newEnd = min/max(rangeStart, D2)`. Jeśli którykolwiek dzień w
     `[newStart, newEnd]` jest `--occupied` → **nie** ustawiaj zakresu, zostaw
     poprzedni wybór, pokaż krótki komunikat "Wybrany zakres zawiera zajęty dzień."
     Inaczej ustaw zakres, podświetl cały przedział na zielono.
3. Kompletny zakres już wybrany → kolejny klik wolnego dnia zaczyna **nowy** wybór od
   tego dnia (reset), zamiast rozszerzać — standardowy wzorzec z popularnych pickerów
   zakresu dat.
4. Nawigacja miesiącem (`data-cal-nav`, wzorem `bindCalendarNav`,
   `basen_module.js:940-949`) **nie kasuje** wybranego zakresu — komórki w aktualnie
   wyświetlanym miesiącu, które mieszczą się w zakresie (nawet z innego miesiąca),
   renderują się na zielono (proste porównanie stringów ISO).
5. Pod siatką stały wiersz podsumowania: "Kliknij dzień startu" → "Kliknij dzień
   końca" → "Wybrany termin: 5–8 lipca 2026 (4 dni)" — czytelna, łatwo weryfikowalna
   informacja bez liczenia dni na oko.
6. `onRangeChange(startIso, endIso)` wywoływane przy każdej zmianie — wołający
   (gear_module.js / my_reservations_module.js) synchronizuje ukryte natywne
   `<input type="date">`, które zostają w DOM (`hidden`) jako jedyne źródło prawdy dla
   istniejącego kodu zapisu — **żeby nie ruszać `checkBundleAvailability` /
   `submitBundleReservation` / logiki zapisu edycji**, tylko podmienić sposób, w jaki
   te pola są wypełniane. Przycisk "Zapisz rezerwację"/"Zapisz zmiany" zostaje
   zablokowany, dopóki `onRangeChange` nie zwróci kompletnego zakresu.

### CSS

Nowa sekcja w `public/styles/gear.css` (nie w `basen.css` — gear ma własny plik, wzorem
istniejącego podziału). Klasy `.gearCal*`, kolory `#f59e0b` / `#22c55e` zgodne z już
używanymi w aplikacji tokenami (spójność, nie nowy branding). Breakpoint mobilny
analogiczny do `basen.css:667-673` (mniejsze ikony/gap poniżej 720px), `aspect-ratio:1/1`
na komórkach jak w `.basenCalDay` — sprawdzony wzorzec bez rozjeżdżania siatki 7-kolumnowej
na wąskich ekranach.

## Backend: rozszerzenie endpointu zajętych terminów

`GET /api/gear/kayak-reservations` (`functions/src/api/getKayakReservationsHandler.ts`,
funkcja `getKayakReservations`, wpis w `firebase.json:266-270`) dziś działa tylko dla
kajaków (`kayakIds array-contains kayakId`). **Zostaje ta sama ścieżka i nazwa funkcji**
(zero zmian w `firebase.json` — pamiętany gotcha: nowa/przeniesiona funkcja wymaga
ręcznego wpisu rewrite, więc unikamy tworzenia nowego route'a i po prostu rozszerzamy
istniejący):

- Nowe opcjonalne parametry: `category` (domyślnie `"kayaks"`, wzorem
  `isSupportedBundleCategory` z `gear_bundle_service.ts:63-65`), `itemId` (nowy,
  generyczny — `kayakId` zostaje jako alias, żeby nie ruszać istniejącego wywołania w
  sekcji "Więcej" na karcie kajaka), `excludeReservationId` (do edycji — pomija własną
  rezerwację przy liczeniu zajętości).
- Zapytanie generalizowane wzorem `findBundleConflicts`
  (`gear_bundle_service.ts:437-480`): dla `category === "kayaks"` dwa zapytania —
  `itemIds array-contains "kayaks/{id}"` (nowy format) ORAZ `kayakIds array-contains
  {id}` (dokumenty sprzed refaktoru bundli) — połączone i odduplikowane po ID
  dokumentu. Dla pozostałych kategorii wystarczy samo `itemIds array-contains
  "{category}/{id}"` (te dokumenty zawsze mają już format bundlowy). Reużyć
  `compositeId()` z `gear_bundle_service.ts:59-61` (API handlery już dziś importują z
  tego modułu, np. `gearReservationCreateHandler.ts`).
- Reszta logiki bez zmian: filtr `blockEndIso >= dziś`, batch-dociąganie
  `userDisplayName` z `users_active`, sortowanie po `startDate`.
- Odpowiedź: `{ ok, category, itemId, reservations: [{startDate, endDate,
  blockStartIso, blockEndIso, userDisplayName}] }` — te same pola co dziś, tylko
  generyczne `category`/`itemId` obok.

## Frontend: integracja

### `public/modules/gear_module.js` — modal tworzenia (`#gearBundleModal`)

- Wiersze "Data od"/"Data do" (linie ~330-338) → kontener kalendarza
  `<div id="bundleDateCalendar">`, oba `<input type="date">` zostają w DOM jako
  `hidden` (źródło prawdy dla `checkBundleAvailability`/`submitBundleReservation`,
  które **nie wymagają zmian logiki**, tylko czytają `.value` jak dziś).
- `startBundleForItem(itemId, category, label)` (linia 632): po ustawieniu starter
  itemu — fetch zajętych zakresów przez rozszerzony endpoint
  (`category=${category}&itemId=${itemId}`) i inicjalizacja
  `createReservationCalendar(...)` w `#bundleDateCalendar`, z `onRangeChange`
  ustawiającym `bundleStartDateEl.value`/`bundleEndDateEl.value` +
  włączającym/wyłączającym `bundleCreateBtn`.
- Kalendarz pilnuje occupied-day tylko dla **starter itemu** (tego, na którym kliknięto
  "Rezerwuj") — pozostała logika dodawania kolejnych przedmiotów z innych kategorii do
  tej samej rezerwacji (`checkBundleAvailability`, chipy "Sprawdź dostępność",
  `gear_module.js:646-694`, `749-808`) zostaje bez zmian jako istniejący,
  autorytatywny mechanizm sprawdzania dostępności dla przedmiotów dodawanych po
  wybraniu terminu.
- **Czyszczenie martwego kodu**: legacy modal `#gearReservationModal` (linie 262-311)
  wraz z całą jego obsługą (`startCreateForKayak`, `openReservationModal`,
  `closeReservationModal`, `syncReservationForm`, `clearReservationForm`,
  `submitCreateReservation`, referencje elementów `reservation*`,
  `CREATE_RESERVATION_URL`, handler `data-gear-reserve` w delegacji kliknięć) — do
  usunięcia. Agent eksploracyjny potwierdził brak jakiegokolwiek renderowanego
  przycisku `data-gear-reserve` w bieżących szablonach kart (tylko
  `data-gear-bundle-reserve` jest emitowane) — przed usunięciem zweryfikować to jeszcze
  raz grepem `data-gear-reserve=` po całym `public/`, żeby nie skasować czegoś żywego.
- Sekcja "Więcej" na karcie kajaka (lazy-load `loadAndRenderReservations`, linie
  1531-1539) zostaje **bez zmian** — to zwykły podgląd tekstowy, nie miejsce wyboru
  daty, poza zakresem tej zmiany; nadal wywołuje ten sam endpoint z `kayakId` (alias
  działa bez modyfikacji wywołania).

### `public/modules/my_reservations_module.js` — edycja terminu

Dwa miejsca, ten sam wzorzec co wyżej:
- Modal edycji z listy (`#reservationEditModal`, linie 65-100): pola
  `#reservationEditStartDate`/`#reservationEditEndDate` → ukryte, nad nimi kalendarz.
- Dedykowany widok edycji (`renderDedicatedEditView`, linie ~383-542): analogicznie dla
  jego pary pól dat (~438-446).
- W obu przypadkach: przedmiot do wyznaczenia zajętości = element pierwotny
  rezerwacji — `primaryCategory`/`primaryItemId` (format bundlowy) z fallbackiem do
  `kayakIds[0]` + `category:"kayaks"` (legacy), dokładnie tą samą logiką co już
  istniejący `getReservationKayakTitles` (`my_reservations_module.js:546-556`) używa do
  tytułu. Fetch z `excludeReservationId=<id edytowanej rezerwacji>`, żeby własny,
  aktualny termin nie pokazywał się jako "zajęty" blokujący samego siebie.
- Zapis (`UPDATE_RESERVATION_URL` POST) zostaje bez zmian — czyta `.value` ukrytych
  inputów jak dziś.

## Weryfikacja

1. `npm --prefix functions run build` + `npm --prefix functions run lint`.
2. Ręcznie w przeglądarce (prod, `morzkulc-e9df7.web.app` — dev jest nieaktualny):
   - Otwórz "Rezerwuj" na kajaku z istniejącą rezerwacją → zajęte dni pomarańczowe +
     kłódka, klik pokazuje kto/kiedy.
   - Klik wolnego dnia startu → zielony pojedynczy dzień, klik dnia końca → cały
     zakres zielony, podsumowanie tekstowe poprawne, przycisk "Zapisz rezerwację"
     odblokowany dopiero teraz.
   - Próba wybrania zakresu przechodzącego przez zajęty dzień → odrzucone z
     komunikatem, poprzedni wybór zostaje.
   - Nawigacja do następnego miesiąca z niedomkniętym/domkniętym zakresem → zakres
     nie znika, poprawnie podświetlony w nowym miesiącu.
   - To samo dla innej kategorii (np. wiosło) — kalendarz działa identycznie.
   - Edycja istniejącej rezerwacji (lista + widok dedykowany) → własny bieżący termin
     NIE pokazuje się jako zajęty, zmiana zakresu i zapis działa.
   - Widok mobilny (wąski viewport) — siatka nie rozjeżdża się, kłódka i cyfry
     czytelne, dotyk działa (nie tylko hover).
3. Backend: scenariusz z audytu `18.06_rezerwacje_czas_audyt_TO_DO.md` (horyzont/
   długość) nadal działa identycznie — kalendarz nie zmienia tych reguł, błąd nadal
   wyświetla się jak dziś, jeśli użytkownik wybierze poprawny-wg-kalendarza, ale
   za długi/za odległy zakres.
4. Deploy: `firebase deploy --only functions` (handler), potem
   `firebase deploy --only hosting` (frontend) — bez ponownej autoryzacji, zgodnie z
   ustaloną zasadą, że deploy robi Claude, commit tylko user.
