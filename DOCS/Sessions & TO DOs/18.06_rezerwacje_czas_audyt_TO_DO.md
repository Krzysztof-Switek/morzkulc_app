## CZĘŚĆ 1 — WYNIKI AUDYTU

### 1.1 Przyczyna źródłowa
Jeden check miesza dwa różne pojęcia. Funkcja `maxEndIsoByWeeks(weeks)` (`functions/src/modules/calendar/calendar_utils.ts:36`) zwraca **dziś + tygodnie×7** i jest porównywana z **datą zakończenia** rezerwacji:
```ts
const maxEndIso = maxEndIsoByWeeks(maxWeeks);
if (args.endDate > maxEndIso) { ... code: "max_time_exceeded" ... }
```
Dziś = 18.06, `członek_max_time` = 2 (domyślne) → maks. koniec = **02.07**. Rezerwacja kończąca się 18.07 jest odrzucana, mimo że jej długość to dokładnie 14 dni.

To jest w istocie kontrola **horyzontu** („jak daleko w przyszłość"), a nie **długości** („na jak długo"). Frontend natomiast opisuje ten błąd jako „maksymalny czas rezerwacji … na X tyg." (`public/core/user_error_messages.js:77-81`) — mylnie sugeruje długość.

### 1.2 Co naprawdę znaczą zmienne (ważna różnica)
- `zarząd_max_time`, `członek_max_time`, `kandydat_max_time` (w **tygodniach**) = **horyzont**: jak daleko od dziś można rezerwować. Cel: użytkownicy rezerwują na bieżąco, nie na miesiące do przodu. **NIE** mówią nic o długości rezerwacji.
- **Brak** zmiennej kontrolującej **długość** rezerwacji — to luka do uzupełnienia.

### 1.3 Skąd biorą się limity (i sprawa „brakującej zmiennej w arkuszu")
- `setup_gear_vars.ts` czyta limity z dokumentu `setup/vars_gear` (klucze: `członek_max_time`, `zarząd_max_time`, `kandydat_max_time`, `*_max_items`, `offset_rezerwacji`, …).
- `setup/vars_gear` jest zasilany z zakładki **SETUP arkusza gear** przez task `setup.syncFromSheet` (`setupSyncFromSheet.ts:175-202`, `:260`). Klucz = **dokładna** wartość kolumny „zmienna nazwa" (bez normalizacji).
- Gdy wiersza w arkuszu brak → `getVar` zwraca `undefined` → obowiązuje **wartość domyślna** w kodzie (`członek_max_time`=2, `zarząd`=4, `kandydat`=1).
- **Wniosek:** brak zmiennej w arkuszu NIE jest przyczyną błędu (limit i tak = 2 tyg. z domyślnej). Przyczyną jest wyłącznie logika horyzont-vs-długość.

### 1.4 Gdzie występuje błąd (cały proces rezerwacji)
Wszystkie typy rezerwacji (sam kajak / kajak + sprzęt dodatkowy / sam sprzęt) tworzy `createBundleReservation`. Edycję dat obsługuje `updateGearReservationDates`, która routuje do `updateBundleReservationDates` (nowe rezerwacje) lub legacy `updateReservationDates` (stare, sprzed migracji — wciąż osiągalne). Ten sam błędny check jest w **trzech** żywych miejscach:
- `functions/src/modules/equipment/bundle/gear_bundle_service.ts:470` — `createBundleReservation`
- `functions/src/modules/equipment/bundle/gear_bundle_service.ts:685` — `updateBundleReservationDates`
- `functions/src/modules/equipment/kayaks/gear_kayaks_service.ts:228` — `updateReservationDates` (legacy)

Frontend (`public/modules/gear_module.js`) NIE waliduje dat po stronie klienta (brak `.max`) — błąd przychodzi z backendu.

### 1.5 Offset a długość
Offset (`offset_rezerwacji`, domyślnie 1) rozszerza okno blokady sprzętu na obie strony (`computeBlockIso`), ale NIE jest częścią długości rezerwacji. Długość liczymy od `startDate` do `endDate` włącznie (`daysOnWaterInclusive`, `calendar_utils.ts:46`). Przykład: rezerwacja 14 dni + offset 1 → sprzęt niedostępny 16 dni, ale „długość rezerwacji" = 14.

## CZĘŚĆ 2 — DECYZJE (zatwierdzone)

1. **Horyzont** (`*_max_time`) ma dotyczyć **daty ROZPOCZĘCIA** rezerwacji (zmiana z obecnej daty zakończenia). Spójne z „jak daleko mogę zarezerwować" i nie karze długich rezerwacji.
2. Wprowadzić **jedną wspólną** zmienną **`max_reservation_length`** (w **dniach, włącznie**, domyślnie **14**), ustawianą w zakładce SETUP arkusza gear → sync → `setup/vars_gear`.
3. Długość liczona od `startDate` do `endDate` (offset wykluczony).

## CZĘŚĆ 3 — PLAN WDROŻENIA

### 3.1 `functions/src/modules/calendar/calendar_utils.ts`
- Zmiana nazwy `maxEndIsoByWeeks` → `maxStartIsoByWeeks` (ciało bez zmian: `today + weeks*7`; semantyka: najpóźniejsza dozwolona data startu).
- Reużyć istniejące `daysOnWaterInclusive(start, end)` do checku długości.

### 3.2 `functions/src/modules/setup/setup_gear_vars.ts`
- Dodać do `GearVars` pole `maxReservationLengthDays: number`.
- W `getGearVars`: `const maxReservationLengthDays = toNumber(getVar(raw, "max_reservation_length"), 14);` i zwrócić w obiekcie.
- Wartość globalna — czytana jako `vars.maxReservationLengthDays` (bez akcesora per rola).

### 3.3 Trzy miejsca walidacji — wzorzec zamiany
W `gear_bundle_service.ts` (`createBundleReservation` ≈`:470`, `updateBundleReservationDates` ≈`:685`) oraz `gear_kayaks_service.ts` (`updateReservationDates` ≈`:228`):

zastąpić:
```ts
const maxEndIso = maxEndIsoByWeeks(maxWeeks);
if (args.endDate > maxEndIso) {
  return {ok:false, code:"max_time_exceeded", message:"Too far in future", details:{maxWeeks}} as const;
}
```
na:
```ts
// Horyzont — jak daleko od dziś można ZACZĄĆ rezerwację
const maxStartIso = maxStartIsoByWeeks(maxWeeks);
if (args.startDate > maxStartIso) {
  return {ok:false, code:"max_time_exceeded", message:"Start too far in future", details:{maxWeeks}} as const;
}
// Długość — maks. liczba dni włącznie (start→end, bez offsetu)
const maxLenDays = vars.maxReservationLengthDays;
if (maxLenDays > 0 && daysOnWaterInclusive(args.startDate, args.endDate) > maxLenDays) {
  return {ok:false, code:"max_length_exceeded", message:"Reservation too long", details:{maxDays: maxLenDays}} as const;
}
```
- Importy: dodać `daysOnWaterInclusive`, zamienić `maxEndIsoByWeeks` → `maxStartIsoByWeeks` w obu plikach. `vars` jest już dostępne w każdej z funkcji.

### 3.4 `public/core/user_error_messages.js`
- `max_time_exceeded` → przeredagować na horyzont: „Nie możesz rezerwować tak daleko w przyszłość. Rezerwacja może zaczynać się maksymalnie X tyg. od dziś." (X = `details.maxWeeks`).
- Dodać `max_length_exceeded`: „Rezerwacja może trwać maksymalnie N dni." (N = `details.maxDays`).

### 3.5 Operacyjnie (arkusz gear, zakładka SETUP)
- Dodać wiersz: „zmienna nazwa" = `max_reservation_length`, „wartość zmiennej" = `14`. Uruchomić „Morzkulc → sync setup". Weryfikacja: `setup/vars_gear.vars.max_reservation_length` w Firestore.
- Ustawić horyzont per rola na właściwą liczbę tygodni (`członek_max_time` itd.) — inaczej obowiązują domyślne (członek=2). Uwaga: aby rezerwacja startująca 05.07 przeszła, horyzont musi pozwalać start ~3 tyg. od dziś (np. `członek_max_time` ≥ 3–4).
