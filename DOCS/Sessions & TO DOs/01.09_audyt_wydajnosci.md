# Audyt wydajności — 01.09.2026

Audyt kodu (bez zmian w kodzie). Cel: miejsca powodujące spowolnienia, zawieszenia, zbędne powtórzenia pracy — frontend + backend.

## Podsumowanie

- **10 pozycji** w tabeli głównej: 2 frontend, 8 backend. Podział wg dotkliwości: **5 pozycji realny efekt przy obecnej skali dziś**, **5 pozycji ryzyko skalowania (nie problem dziś)**.
- **Naprawa w `basen_module.js` (nasłuchiwacz na `#basenInner` mnożący się przy każdym odświeżeniu) jest KOMPLETNA** — zweryfikowane linia po linii: `bindModalCloseDelegation`/`bindCalendarModalCloseDelegation` wołane wyłącznie raz, z `render()` (linie 1417-1418), z komentarzem wyjaśniającym. Trzeci nasłuchiwacz na `innerEl` w tym pliku (`renderPaymentsTab`, linia 1294) sprawdzony osobno — bezpieczny, bo otaczająca funkcja `draw()` jest wołana tylko raz na wejście do zakładki.
- **Znaleziono DODATKOWE wystąpienie tego samego wzorca w innym pliku** — `public/modules/km_module.js`, funkcja `attachInfoTips` (patrz #1 w tabeli). To NIE jest ta sama naprawiona lokalizacja — osobny, wciąż aktywny bug tej samej klasy.
- Wszystkie pozostałe moduły sprawdzone linia po linii pod tym samym wzorcem (nasłuchiwacz na stabilnym elemencie, bindowany w funkcji wołanej wielokrotnie): `gear_module.js`, `godzinki_module.js`, `impreza_module.js`, `kurs_module.js`, `kurs_godzinki_module.js`, `klub_module.js`, `my_reservations_module.js`, `admin_pending_module.js`, `raporty/*.js`, `render_shell.js` — **czyste**. `gear_module.js` i `my_reservations_module.js` dodatkowo mają świadomie wdrożony `AbortController` + `MutationObserver` na nasłuchiwaczu `window.addEventListener("keydown", ...)`, żeby uniknąć dokładnie tego problemu — wzorzec do skopiowania przy naprawie #1.
- Debounce na polach szukajki: sprawdzone we wszystkich miejscach (`gear_module.js`, `raporty/gear_rentals.js`, `raporty/reports_panel.js`, `basen_module.js` płatności) — **wszystkie filtrują już załadowaną tablicę w pamięci, zero zapytań API na klawisz** → debounce faktycznie niepotrzebny przy obecnej skali. Jedyny prawdziwy autocomplete z zapytaniem API (`km_module.js`, nazwy akwenów) **już ma** debounce 300 ms/min 2 znaki.
- Wzorce O(n²) (zagnieżdżone `.find()`/`.filter()` w `.map()`): nie znaleziono żadnego w `public/modules/**`. Listy uczestników w `basen_module.js` używają `Map` do lookupu (O(n)), nie zagnieżdżonego `.find()`.
- Kontencja transakcji Firestore: zbadana dla `basen_service.ts` (`enrollInSlot`/`cancelSession`/`claimWaitingStudent` — wszystkie modyfikują współdzielony dokument `basen_sessions/{sessionId}` w transakcji). Realne ryzyko dziś: **niskie/teoretyczne** — patrz #10.

## Weryfikacje bez wyniku (sprawdzone, potwierdzone jako niebędące problemem)

- **Debounce na polach szukajki** — wszystkie pola filtrujące w aplikacji (`gear_module.js`, `raporty/gear_rentals.js`, `raporty/reports_panel.js`, `basen_module.js` zakładka Płatności) operują na już pobranej tablicy w pamięci (czysty JS `.filter()`), zero wywołań API na klawisz. Jedyny autocomplete z realnym zapytaniem API (nazwy akwenów w `km_module.js:236-254`) ma już debounce 300 ms + próg 2 znaków.
- **Wzorce O(n²)** — brak w `public/modules/**`. Listy uczestników basenu budują `Map` do lookupu instruktora (`basen_module.js:133`), nie zagnieżdżony `.find()` w `.map()`.
- **Duplikowane wywołania API w jednym cyklu renderowania** — nie znaleziono. Endpointy `/api/km/kursant-stats` i `/api/godzinki?view=home` są wołane w DWÓCH różnych, wzajemnie wykluczających się widokach (dashboard startowy vs. widok profilu) — to nie jest podwójne wywołanie w jednym cyklu, tylko niezależne odświeżenia różnych ekranów.
- **`public/sw.js`** — poza już zgłoszoną luką w precache (osobny audyt), strategia cache (network-first dla nawigacji, cache-first dla assetów statycznych, zawsze-sieć dla `/api/*`) jest poprawna i nie generuje dodatkowego obciążenia.
- **Timery (`setInterval`/`setTimeout`)** — jeden `setInterval` w całej aplikacji (`app_shell.js:60`, cykliczny check aktualizacji SW co 20 min) — rejestrowany raz na cały cykl życia aplikacji, nie w funkcji renderującej, brak ryzyka mnożenia. Wszystkie `setTimeout` w modułach to jednorazowe opóźnienia UI (np. komunikat „zapisano", podświetlenie karty) — nie wymagają `clearTimeout`.
