# Audyt IAM invoker funkcji (public vs require-auth) — wyjaśnienie i klasyfikacja

Data: 2026-06-15 (skorygowane)
Projekt prod: `morzkulc-e9df7` · region `us-central1`

---

## ⭐ DWIE RÓŻNE „AUTORYZACJE" — sedno

**Warstwa 1 — Cloud Run „Uwierzytelnianie" (Public access / Require authentication):** kto w ogóle może dotrzeć do KODU funkcji. To Google IAM. „Uwierzytelniony" = tożsamość Google IAM (konto serwisowe), NIE zalogowany użytkownik aplikacji.

**Warstwa 2 — kod funkcji (`requireIdToken` + lista hostów):** gdy request wejdzie do kodu — sprawdza token Firebase zalogowanego usera i domenę. Osobna bramka.

**Pułapka:** token Firebase użytkownika ≠ token Google IAM. Więc „Require authentication" NIE znaczy „wpuść zalogowanych" — znaczy „wpuść tylko wywołującego z tożsamością IAM" (Hosting SA, Cloud Scheduler, Eventarc). Przeglądarka użytkownika nigdy jej nie ma.

**„Public access" ≠ bez ochrony:** kod i tak odrzuca brak tokenu Firebase / zły host. Public access tylko pozwala requestowi dotrzeć do kodu; realne bezpieczeństwo robi token w handlerze.

---

## Dlaczego „Require authentication" psuje funkcje w aplikacji

Frontend woła WYŁĄCZNIE względne `/api/...` (potwierdzone: `public/core/api_client.js` + `firebase.json` rewrites). Ścieżka: przeglądarka → `*.web.app/api/...` → **Firebase Hosting** → Hosting wywołuje funkcję Cloud Run.

- Funkcja **Public access**: Hosting zawsze ją wywoła → działa.
- Funkcja **Require authentication**: Hosting wywoła ją tylko, jeśli konto serwisowe Hostingu ma `roles/run.invoker` na tej funkcji. `firebase deploy` nadaje to NIEKONSEKWENTNIE (nowe — tak; istniejące — pomija). Brak → Hosting dostaje 403 → funkcja w aplikacji nie działa. (To był bloker approve/reject 13.06.)

Dlatego przełączanie funkcji HTTP na require-auth „psuje funkcjonalności" — to obserwacja właściciela, w pełni poprawna.

## Stan rzeczywisty = konsola Cloud Run (mix), NIE „wszystko prywatne"

**KOREKTA:** wcześniejsza wersja tego dokumentu (i teza „wszystko prywatne, PUBLIC:0") była BŁĘDNA. Powody błędu:
1. Test bezpośredni `*.run.app` bez tokenu zwracał 403 dla wszystkich — ale to 403 z KODU (`requireAllowedHost` odrzuca host `*.run.app`, bo nie ma go w `ALLOWED_HOSTS`), a NIE z IAM. Daje 403 i dla public, i dla private → nie rozróżnia.

**Źródło prawdy: konsola Google Cloud → Cloud Run → Usługi, kolumna „Uwierzytelnianie".** Stan jest mieszany i spójny z pierwotną listą właściciela.

## Klasyfikacja docelowa (co z czym)

| Grupa | Ustawienie docelowe | Dlaczego |
|---|---|---|
| Funkcje HTTP wołane przez `/api/...` (większość: get*, submit*, gear*, basen*, km*, admin*, kurs*, userWeight, appsScriptSync, kmMapData) | **Public access** | Hosting zawsze je wywoła; token w kodzie chroni. Require-auth psuje, dopóki Hosting SA nie dostanie ręcznie invokera na każdej |
| Schedulery: `gearPrivateStorageMonthly`, `usersSyncRolesDaily`, `eventsSyncSheetDaily`, `eventsSyncCalendarDaily`, `kmRebuildMapMonthly`, `godzinkiSyncDaily`, `adminPendingNotifyDaily`, `serviceFallbackDaily` | **Require authentication** | Woła je Cloud Scheduler tożsamością IAM, nie przeglądarka. Bezpieczne i nic nie psuje |
| Triggery: `onServiceJobCreated`, `onUsersActiveCreated` | **Require authentication** | Woła je Eventarc tożsamością IAM. Bezpieczne |

Uwaga praktyczna: niektóre funkcje HTTP w konsoli są „Require authentication" i działają (np. `getBasenGodziny`, `basenAdminSearchUsers`, `kmAdminMergePlaces`) — bo akurat dla nich Hosting SA ma nadany invoker. To stan kruchy: kolejny redeploy może go zgubić i wtedy się zepsują. Jeśli któraś funkcja HTTP nagle przestanie działać → najpierw sprawdź, czy nie jest „Require authentication" bez invokera dla Hosting SA; najprościej przełączyć na Public access (token w kodzie nadal chroni).

## Rekomendacje

1. **Nie przełączaj funkcji HTTP (`/api/...`) na Require authentication** w nadziei „tylko zalogowani" — to nie to robi i psuje ścieżkę Hostingu. Bezpieczeństwo daje token w kodzie.
2. **Schedulery i triggery — zostaw / ustaw Require authentication.** `gearPrivateStorageMonthly` już przełączone (15.06) — OK, scheduler, nie psuje appki.
3. Jeśli kiedyś chcesz funkcję HTTP zamknąć na require-auth „na serio" — nadaj jawnie `roles/run.invoker` dla agenta Hostingu na tej funkcji (NIE upubliczniaj przez allUsers, ale i NIE licz, że deploy zrobi to sam).
