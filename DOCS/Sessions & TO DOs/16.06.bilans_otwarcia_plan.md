## Context

Klub kończy okres przejściowy ze starego systemu (arkusze Google) na aplikację. W arkuszu `bilans_otwarcia_26` są już **pełne dane** członków — w tym salda **godzinek** i **składek**. Dodatkowo istnieją **tegoroczne transakcje godzinek spoza bilansu** (zgłoszenia pracy + potrącenia za prywatne kajaki/wypożyczenia) dla osób, które **jeszcze się nie zarejestrowały** (brak `uid`).

Cele:
1. Powtarzalny import **wszystkich pól** arkusza bilansu → kolekcja `users_opening_balance_26`.
2. Przy rejestracji: **wszystkie dane bilansu trafiają do `users_active`** danego użytkownika (po rejestracji aplikacja nie sięga już do bilansu).
3. Salda godzinek/składek z bilansu **zasilić jednorazowo kolumny arkusza członków**.
4. Godziny **lump-sum z bilansu otwarcia** wygasają **30.06.2029** (dziś zakodowane 31.12.2029).
5. Zaimportować **tegoroczne transakcje godzinek** dla osób niezarejestrowanych do `godzinki_ledger` pod `uid="hist_{email}"`; po rejestracji task km-style przepisuje `hist_{email}`→prawdziwy `uid`. Arkusz pozostaje narzędziem ręcznych korekt **do końca września 2026**.

Stan obecny (potwierdzony w kodzie):
- `users_opening_balance_26` **nie jest zapisywana żadnym kodem** — import był ręczny/jednorazowy. Odczyt: `findOpeningBalance` (`functions/src/api/registerUserHandler.ts:223`), iteruje całą kolekcję, dopasowuje po polu `e-mail`, fallback po `imię`/`imie`+`nazwisko`.
- Rejestracja już zapisuje `openingBalance` = cały wiersz do `users_active` (`registerUserHandler.ts:533`) i kredytuje godziny przez `creditOpeningBalance` (`functions/src/modules/hours/godzinki_service.ts:896`), data wygaśnięcia `OB_HOURS_EXPIRES_AT` (`registerUserHandler.ts:331`).
- `godzinki_ledger` (`godzinki_service.ts:60`): typy `earn`/`spend`/`purchase`, saldo = Σ`earn.remaining`(approved, niewygasłe) − net_overdraft. Kluczowane po `uid`.
- **Wzorzec danych sprzed rejestracji już istnieje**: `km_logs` z `uid="hist_{email}"` + task `km.mergeHistoricalUser` (`functions/src/service/tasks/kmMergeHistoricalUser.ts`) przepisuje `hist_{email}`→prawdziwy uid; enqueue w `enqueueKmHistoricalMerge` (`registerUserHandler.ts:262`). **Plan kopiuje ten wzorzec 1:1 dla godzinek** (Workstream C).
- Apps Script (projekt „członkowie sympatycy SKK") ma helpery REST: `firestoreCommitDocuments_`, `firestorePatchDocument_`, `firestoreGetDocument_`, `toFirestoreValue_` (`common_helpers.gs:171+`). Stałe: `TAB_OPENING_BALANCE="bilans_otwarcia_26"`, `TAB_USERS="członkowie i sympatycy"`, `TAB_HOURS="godzinki"`, `USERS_ARCHIVE_SPREADSHEET_ID`, `USERS_SPREADSHEET_ID` (`env_config.gs`).
- Arkusz członków: kolumny **Składki**/**Godzinki** już istnieją (tekst), płyną arkusz→Firestore przez `usersSyncFieldsFromSheet.ts`→`admin.contributions`/`admin.hours`. `membersSyncToSheet.ts` ich **nie nadpisuje** — zasilenie jest bezpieczne.

Decyzje (zatwierdzone): tegoroczne godziny = `hist_{email}` w `godzinki_ledger` (Opcja 1); import godzinek = task w Functions (FIFO przez `deductHours`); import bilansu = Apps Script; potrącenia = ujemne „Godzinki"; klucz tożsamości = kolumna E-mail; arkusz członków = jednorazowe zasilenie kolumn; wygasanie 30.06.2029 **tylko** lump-sum bilansu.

## Workstream C — Functions: import przejściowy godzinek (`hist_{email}` w godzinki_ledger + scalenie km-style)
Model: **jedna kolekcja `godzinki_ledger`**. Osoby niezarejestrowane → rekordy pod `uid = "hist_{email}"` (wzór `km_logs`). Rekordy `hist_…` są „uśpione" (żaden ekran ich nie pyta, nie wpływają na cudze saldo) do czasu rejestracji. Saldo liczone tym samym `computeBalance`.

### C1 — Task importu `godzinki.importTransitionFromSheet` (nowy, w Functions)
Plik: `functions/src/service/tasks/godzinkiImportTransitionFromSheet.ts`; rejestracja w `registry.ts`.
- Czyta zakładkę „Godzinki 2026 i korekty" („DECODER KSYWEK I SKŁADKI") przez `GoogleSheetsProvider.readTableAsObjects` (wzór: `godzinkiSyncFromSheet.ts:189`). Spreadsheet/tab z payloadu lub configu.
- Dla każdego wiersza **bez `ID`** (nowy rekord):
  1. **Ustal uid**: query `users_active` po `E-mail`. Znaleziony → prawdziwy uid; brak → `hist_{email}` (lowercase, trim).
  2. **Twórz rekord przez funkcje serwisowe** (poprawne FIFO/remaining):
     - `Godzinki` > 0 (earn) → zatwierdzony `earn` (`grantedAt` = „Data pracy", `expiresAt = grantedAt + expiryYears` wg `getGodzinkiVars`; **normalne wygasanie**, nie 30.06.2029),
     - `Godzinki` < 0 (spend) → `deductHours(..., {force:true})` na tym uid (jak `gearPrivateStorage.ts:247`).
  3. Przetwarzaj wiersze danej osoby **chronologicznie** (po „Data pracy"): earny przed konsumującymi je potrąceniami.
  4. **Dopisz wygenerowane `ID`** do kolumny `ID` + `Zsynchronizowano` w arkuszu (`upsertMemberRowById`, jak `godzinkiSyncFromSheet.ts:328`).
- Idempotencja: wiersz z `ID` + `Zsynchronizowano` pomijany (fast-path `godzinkiSyncFromSheet.ts:232`).

### C2 — Bieżące korekty (okres przejściowy do końca IX 2026) — ZREALIZOWANE w tasku importu
- Korekta = **nowy wiersz** w zakładce (np. `+3` lub `-2`) z `Zatwierdzone=TAK`. Ponowne uruchomienie `godzinki.importTransitionFromSheet` tworzy nowy rekord pod właściwym uid (prawdziwy gdy zarejestrowany, `hist_{email}` gdy nie). Idempotencja przez kolumnę `Zsynchronizowano` (wiersze już zaimportowane są pomijane).
- **Nie modyfikujemy** `godzinkiSyncFromSheet` — to samo narzędzie (import) obsługuje początkowy import i bieżące korekty jako kolejne wiersze.

### C3 — Scalenie przy rejestracji: task `godzinki.mergeHistoricalUser` (nowy, klon `kmMergeHistoricalUser.ts`)
Plik: `functions/src/service/tasks/godzinkiMergeHistoricalUser.ts`; rejestracja w `registry.ts`.
- payload `{uid, email, histUid}`; idempotencja markerem `users_active.service.godzinkiHistMergedFrom`.
- batch-update (≤400) wszystkich `godzinki_ledger` z `uid == hist_{email}` → prawdziwy uid; ustaw marker.
- **FIFO przetrwa** — `spend.earnDeductions` wskazuje na `earnId` (id dokumentów), niezmieniane przy podmianie uid. Brak replay.
- **Enqueue przy rejestracji**: `enqueueGodzinkiHistMerge(db, admin, uid, email)` w `registerUserHandler.ts` (kopia `enqueueKmHistoricalMerge` `:262`): probe `godzinki_ledger.where("uid","==","hist_"+email).limit(1)`, `jobId = godzinki-hist-merge:{uid}`, wołane dla nowego i istniejącego usera (jak km `:473`/`:574`).

## Workstream E — Functions: reconciliation już-zarejestrowanych (jednorazowy task)
**Problem:** front przy logowaniu woła `/api/register` z body `{hello:"world"}` (`app_shell.js:135`) — bez profilu. Plik: `functions/src/service/tasks/reconcileOpeningBalance.ts` (nowy); rejestracja w `registry.ts`. Uruchamiany **raz** po imporcie (A), przed otwarciem rejestracji.

- Przy trafieniu: ustaw pola `admin.*` (jak Workstream B) oraz `openingMatch/openingMatchMethod/openingBalance/openingMatchedAt` gdy brakuje.
- Popraw rekord lump-sum w `godzinki_ledger` (earn z `approvedBy="opening_balance"` dla tego uid): ustaw `amount`/`remaining` = aktualne `getObHours`, `expiresAt = 30.06.2029`. - **Idempotentny** — bezpieczny do ponownego uruchomienia.
