# Czytelne wyświetlanie opisów imprez (pełna lista + widget na stronie głównej)

**Status: WDROŻONE na prod (morzkulc-e9df7) 20.08.2026**

## Kontekst

Użytkownicy wpisują opisy imprez jako surowy, długi tekst: dużo enterów (często
3+ pod rząd), emotki, wklejone linki. W pełnej liście imprez ten tekst wyświetla się
nieczytelnie — nadmiarowe odstępy między akapitami, a długie linki wystają poza kartę
na telefonie (brak jakiegokolwiek `overflow-wrap`/`word-break` w CSS). Priorytet:
telefon, ale ma wyglądać dobrze też na www.

Ten sam `description` renderowany jest w DWÓCH miejscach z DWOMA różnymi babolami:
- pełna lista (`impreza_module.js`) — enter'y są zachowywane (`white-space: pre-line`),
  więc 3+ entery = duża pusta przestrzeń; brak wrap → długie linki wystają.
- widget "nadchodzące imprezy" na stronie głównej (`render_shell.js`) — enter'y
  dziś w ogóle znikają (brak `white-space: pre-line`), więc tekst zlewa się w jedną linię.

User potwierdził (AskUserQuestion): naprawiamy oba miejsca wspólnym mechanizmem.

Pole `description` to zwykły `<textarea maxlength="1000">` bez żadnej walidacji
formatu (`impreza_module.js:169-172`) — naprawa jest wyłącznie po stronie renderowania,
input się nie zmienia.

## Architektura naprawy

**Nowy wspólny moduł:** `public/core/text_format.js`, eksportuje `formatFreeText(raw)`.

Uzasadnienie dla wspólnego pliku (zamiast kopiować lokalny `esc()` jak w reszcie
projektu): to nie jest trywialny jednolinijkowy escaper jak istniejące kopie —
bezpieczne linkowanie URLi wymaga konkretnej kolejności (regex na SUROWYM tekście,
potem escaping per-segment), a pole i tak jest dziś renderowane w dwóch miejscach z
dwoma rozjechanymi implementacjami. Napisanie raz i zaimportowanie w obu miejscach
usuwa istniejącą niespójność zamiast dokładać trzecią wersję. Nie dotykamy pozostałych
~15 skopiowanych `esc()`/`escapeHtml()` w innych plikach — to wąski, uzasadniony wyjątek
tylko dla tej logiki.

### `formatFreeText(raw)` — algorytm

1. **Normalizacja pustych linii** (na surowym tekście, przed escapingiem):
   ```js
   String(raw ?? "")
     .replace(/\r\n?/g, "\n")
     .replace(/[ \t]+\n/g, "\n")
     .replace(/\n{3,}/g, "\n\n")   // 3+ entery → dokładnie 1 pusta linia
     .trim();
   ```
2. **`escapeHtml(s)`** — jak istniejący `esc()` z `impreza_module.js:14-20`, ale
   dodatkowo escapuje `'` (potrzebne, bo wynik trafia też do atrybutu `href="..."`).
3. **Wykrywanie URLi na SUROWYM (znormalizowanym, jeszcze nie zescapowanym) tekście**:
   ```js
   const URL_RE = /((?:https?:\/\/|www\.)[A-Za-z0-9\-._~:/?#[\]@!$&'()*+,;=%]+)/gi;
   ```
   - Łapie `http://`, `https://`, `www.` — nie łapie gołych domen bez schematu
     (unika fałszywych trafień na godziny typu `10.00` czy skróty `np.`).
   - Allowlist znaków URI, więc emoji i polskie znaki/cudzysłowy nigdy nie wpadają
     do dopasowania — bezpieczne nawet bez spacji przed/po linku.
   - Końcowa interpunkcja (`.,;:!?)]}'"`) doklejona bezpośrednio po URLu jest
     odcinana od linku i wypisywana jako zwykły tekst zaraz po `<a>` (świadomy,
     udokumentowany kompromis — link kończący się faktycznie nawiasem zamykającym
     straci go z hrefa; akceptowalne, nie warto pełnego parsera URI dla tego zakresu).
4. **Bezpieczne złożenie** — split surowego tekstu po regexie URL (naprzemienne
   segmenty tekst/URL dzięki grupie przechwytującej), każdy segment escapowany
   NIEZALEŻNIE (href i widoczny tekst linku osobno, oba z tego samego surowego
   dopasowania) — dokładnie w tej kolejności, żeby escapowany `&` w query stringu
   linku (`?a=1&b=2` → `&amp;`) nie popsuł dopasowania ani hrefa:
   ```js
   const segments = normalized.split(URL_RE);
   segments.map((seg, i) => {
     if (i % 2 === 1) {
       const {url, trailing} = stripTrailingPunct(seg);
       const href = /^www\./i.test(url) ? `https://${url}` : url;
       return `<a href="${escapeHtml(href)}" target="_blank" rel="noopener noreferrer">${escapeHtml(url)}</a>${escapeHtml(trailing)}`;
     }
     return escapeHtml(seg);
   }).join("");
   ```
5. **Emoji**: bez specjalnej obsługi — wszystkie regexy powyżej operują wyłącznie na
   wąskich zakresach ASCII (bez flagi `u`), a surogaty/ZWJ-sekwencje emoji leżą poza
   tymi zakresami, więc nigdy nie zostaną rozcięte. `escapeHtml` podmienia tylko
   `&`/`<`/`>`/`"`/`'` — emoji przechodzą bez zmian.

Kontener HTML nadal polega na CSS `white-space: pre-line` (funkcja NIE zamienia `\n`
na `<br>`) — zgodnie z obecnym podejściem w `.imprezaDesc`.

## Zmiany plik po pliku

1. **`public/core/text_format.js`** (nowy) — `formatFreeText()` jak wyżej.

2. **`public/modules/impreza_module.js`**:
   - import: `import { formatFreeText } from "/core/text_format.js";`
   - linia 80: `esc(ev.description)` → `formatFreeText(ev.description)`.
   - `esc()` zostaje bez zmian, nadal używany dla pozostałych pól (nazwa, daty,
     miejsce, kontakt, link) — to pola jednoliniowe, prosty escaper wystarcza.

3. **`public/styles/events.css`**, `.imprezaDesc` (linie 135-141) — dodać:
   ```css
   overflow-wrap: anywhere;
   word-break: break-word;
   ```
   To samodzielnie rozwiązuje zgłoszony problem z wystającymi linkami na telefonie,
   niezależnie od linkowania. `.imprezaCard` nie jest flexem, więc nie trzeba
   `min-width: 0` na przodkach.

4. **`public/core/render_shell.js`** (widget "nadchodzące imprezy"):
   - import `formatFreeText` obok istniejących importów na górze pliku.
   - linia 1013: `escapeHtml(desc)` → `formatFreeText(desc)`. Pozostałe wiersze
     (`loc`, `contact`, `link`) zostają na lokalnym `escapeHtml()` bez zmian.
   - w markupie tego wiersza dodać drugą klasę, żeby nie ruszać współdzielonej
     `.startEventDetailRow` używanej też przez inne wiersze bez formatowania:
     `class="startEventDetailRow startEventDetailRow--desc"`.

5. **`public/styles/start.css`** — nowa reguła obok `.startEventDetailRow` (linia 249):
   ```css
   .startEventDetailRow--desc {
     white-space: pre-line;
     overflow-wrap: anywhere;
     word-break: break-word;
   }
   ```

6. **`public/sw.js`** — dopisać `"/core/text_format.js",` do `PRECACHE_URLS`
   (obok innych wpisów `/core/*.js`, ok. linii 21-45), żeby nowy plik był
   precache'owany offline jak reszta rdzenia aplikacji.

Brak automatycznych testów dla `public/` (tylko `functions/` ma vitest) — weryfikacja
ręczna przez `firebase emulators:start` (serwuje `public/` + prawdziwe API/Firestore
emulator).

Tekst testowy do wklejenia w formularz zgłoszenia imprezy (mieści się w limicie 1000
znaków), łączący wszystkie trzy przypadki naraz:
```

```

Checklist (najpierw viewport telefonu, np. 360×740, potem desktop ~1280px):
1. Brak poziomego przewijania karty mimo długiego linku.
2. Wielokrotne puste linie skurczone do pojedynczej pustej linii.
3. Oba linki (`https://` i `www.`) klikalne, otwierają się w nowej karcie, przecinek/
   kropka po linku widoczne jako zwykły tekst (nie wchłonięte w href).
4. Emoji renderują się poprawnie, bez rozjechanych encji wokół nich.
5. To samo powtórzone na widgecie "nadchodzące imprezy" na stronie głównej.
6. Test bezpieczeństwa: opis zawierający `<script>alert(1)</script>` oraz
   `" onmouseover="alert(1)` obok linku — nic się nie wykonuje, oba renderują się
   jako bezpieczny tekst.

## Poprawka po pierwszym wdrożeniu — plan nie objął pól `location`/`contact`

User zgłosił po pierwszym deployu: "wszystkie opisy wyglądają dokładnie tak samo,
linki czasem wystają poza okno jak np przy imprezie DEZINTEGRACJA". Weryfikacja na
żywych danych (`events/Bh6D615URN7zJWSZvdUz`) pokazała: ta konkretna impreza ma
**pustą/normalną `description`** (brak 3+ enterów, brak URL) — fix opisu nie miał tam
czego zmienić. Prawdziwy problem: pole **`location`** zawierało surowy 200-znakowy
link do Google Maps, renderowany w zupełnie innym elemencie (`.imprezaMeta`), którego
oryginalny plan nie dotykał — stąd user nie widział żadnej zmiany.

**Fix (ten sam dzień, po deployu #1):**
- `public/styles/events.css` — `overflow-wrap: anywhere; word-break: break-word;`
  przeniesione na `.imprezaCard` (rodzic, dziedziczone przez WSZYSTKIE pola karty:
  nazwa, daty, miejsce, opis, kontakt), zamiast tylko na `.imprezaDesc` — zamyka całą
  klasę tego buga, nie tylko opis.
- `public/modules/impreza_module.js` — `ev.location` i `ev.contact` przełączone z
  `esc()` na `formatFreeText()` (linie ~80, 83) — te pola też bywają wklejonymi
  linkami (potwierdzone na żywym przykładzie), więc też powinny być klikalne i
  bezpiecznie zawijane, nie tylko `description`.
- `public/core/render_shell.js` — to samo dla `loc`/`contact` w widgecie strony
  głównej (linie ~1013, 1015).
- `public/styles/start.css` — `.startEventItem` (kontener wiersza) dostał
  `overflow-wrap`/`word-break` zamiast polegać wyłącznie na `overflow: hidden`
  (które by po prostu ucinało tekst, nie zawijało).
- `public/styles/events.css` — kolor linku (`.imprezaDesc a`) rozszerzony na
  `.imprezaMeta a`, `.imprezaContact a`.

Zweryfikowane bezpośrednio na prawdziwej wartości `location` z eventu DEZINTEGRACJA
(pełny link Google Maps → poprawnie zamieniony na klikalny `<a>`), zdeployowane
(`firebase deploy --only hosting`), potwierdzone przez `curl` że nowy kod faktycznie
jest serwowany z hostingu.

**Uwaga do przyszłej weryfikacji**: pierwsza runda tego samego dnia była
zdeployowana poprawnie, ale user nie widział zmian przez stary cache Service
Workera — wymusić przeładowanie dwukrotnie albo użyć bannera "nowa wersja" w
profilu / `hardReloadApp()` (`public/core/sw_update.js`), zanim uzna się fix za
niedziałający.

## Poprawka #2 — reguła zbyt łagodna na REALNYCH danych (impreza „Igraszki Morskie")

Po fixie #1 user zgłosił: „Igraszki Morskie" nadal ma linie mocno oddalone od
siebie. Sprawdzenie surowego tekstu (`events/UHBNUWhJMlMLCgqnMTPJ.description`,
2358 znaków) pokazało, że oryginalny plan zakładał zły model problemu: żaden
fragment tego tekstu nie ma 3+ newline'ów pod rząd (próg `\n{3,}`, na którym
opierał się fix #1) — autor wciska Enter DWA razy po niemal KAŻDEJ linijce (nawet
jednowyrazowych nagłówkach typu „📍 Gdzie?"), więc cały tekst to spójny ciąg
pojedynczych pustych linii (`\n\n`), a nie sporadyczne "wybuchy" wielu enterów.
Próg 3+ nigdy się nie aktywował.

Po konsultacji z userem (AskUserQuestion — wybrał opcję maksymalnie zwartą):
**`public/core/text_format.js`**, `normalizeBlankLines()` — próg zmieniony z
`\n{3,} → \n\n` (zostaw jedną pustą linię) na `\n{2,} → \n` (usuń WSZYSTKIE puste
linie, każdy Enter to zwykłe przejście do nowej linii, bez odstępu). Zweryfikowane
bezpośrednio na prawdziwym tekście „Igraszek Morskich" — 70 newline'ów wejściowych
→ 37 wyjściowych, zero pozostałych podwójnych newline'ów, treść czytelna i zwarta,
link do kempingu nadal poprawnie zlinkowany. Zdeployowane, potwierdzone przez curl.
