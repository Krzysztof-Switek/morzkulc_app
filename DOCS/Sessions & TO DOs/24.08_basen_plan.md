# Moduł Basen — plan wdrożenia (przebudowa H1/H2/sauna + integracja Sprzęt + instruktorzy)

Data: 2026-08-24
Status: **plan do realizacji, NIE wdrożone, kod jeszcze nie napisany**

## Kontekst

Moduł Basen istnieje w kodzie (11 endpointów, ~2400 linii backend+frontend) ale jest
**wyłączony na produkcji** i oparty na uproszczonym modelu „dowolne pojedyncze sesje".
29.07.2026 ustaliliśmy z użytkownikiem docelową logikę biznesową (dokument
`DOCS/Sessions & TO DOs/29.07_basen_logika_biznesowa.md`) — 24.08 potwierdziliśmy
ostatnie otwarte pytania (sekcja 11 tego dokumentu). Cel tego planu: przebudować moduł
zgodnie z ustaloną logiką, żeby dało się go włączyć na produkcji.

Kluczowe ustalone decyzje (pełna lista w dokumencie 29.07, sekcja 11):
- Model terminu = **H1 + H2 + opcjonalna sauna**, każdy slot niezależny (własny limit,
  własna lista zapisanych).
- Kajaki na basenie = `gear_kayaks` ze `storedAt="Basen"` (mechanizm blokady w module
  Sprzęt **już częściowo istnieje** dla kajaków — trzeba dopisać dla 4 kategorii
  drobnego sprzętu i podłączyć wybór kajaka do zapisu na basen).
- Instruktorzy: zgłaszanie/parowanie jak w starej apce, nagrodę dopisuje ręcznie
  człowiek (skarbnik/opiekun), nie automat.
- Nowe uprawnienie „opiekun basenowy" (lista e-maili z arkusza) — taki sam dostęp do
  panelu Zarządzanie jak zarząd/KR.
- **Kursant dostaje dostęp** do zapisów na basen (zmiana względem stanu obecnego).
- Sauna bez slotu instruktorskiego. Jeden globalny limit miejsc (nie osobny per H1/H2).
  Brak osobnego limitu „miejsc szkoleniowych".
- System „godzin basenowych" (martwy kod, 4 endpointy) — **usuwamy całkowicie**, w tym
  `basenAdminSearchUsers` (potwierdzone drugi raz — formularze admina zostają z ręcznym
  wklejaniem UID/e-maila, jak dziś).

Zero realnych danych produkcyjnych do migracji (1 testowy dokument sesji, 0 zapisów,
0 karnetów) — przebudowa schematu jest bezpieczna, stary testowy dokument po prostu
przestaje być czytany.

## Decyzje projektowe tego planu (żeby zminimalizować niepotrzebne zmiany)

- **Nazwy kolekcji i URL-e endpointów zostają w większości bez zmian** — zmienia się
  KSZTAŁT dokumentów/payloadów, nie same nazwy. Unikamy niepotrzebnego przepisywania
  `firebase.json` rewrites, importów, stałych URL w frontendzie. Wyjątek: nowa kolekcja
  `basen_kayak_allocations` (nowy koncept, nie istniał wcześniej).
- **Deterministyczne ID zamiast query-przed-transakcją** — `basen_enrollments/{sessionId}_{slot}_{uid}`
  i `basen_kayak_allocations/{sessionId}_{slot}_{kayakId}`. To eliminuje race condition
  z audytu (`basen_TO_DO.md`, pkt 8) przy zerowym dodatkowym koszcie, bo i tak
  przebudowujemy model.
- **`basenAdminSearchUsers` i 3 endpointy „godzin basenowych" — usuwamy wszystkie 4**
  (potwierdzone przez użytkownika). Formularze admina zostają z ręcznym UID/e-mailem.
- **Uprawnienia „opiekun basenowy" i „instruktor" jako rozszerzenie istniejącego
  mechanizmu** (`allowed_actions` / pola na `data` w `registerUserHandler.ts`), nie
  nowy, równoległy system — dokładnie wzorem `mentor`/`admin.hasClubKeys` już
  eksponowanych w odpowiedzi `/api/register`.

## Faza A — Backend: nowy model danych (`functions/src/modules/basen/basen_service.ts`)

Przepisać typy i logikę. Kolekcja `basen_sessions` (bez zmiany nazwy), nowy kształt
dokumentu:
```ts
type BasenSlotLabel = "H1" | "H2" | "SAUNA";
type BasenSlot = {
  timeStart: string; timeEnd: string; capacity: number; enrolledCount: number;
  instructorEmail?: string; instructorName?: string; status: "open"|"full"|"cancelled";
};
type BasenSession = {
  id: string; date: string; notes?: string;
  slots: Partial<Record<BasenSlotLabel, BasenSlot>>; // zawsze H1+H2, SAUNA opcjonalnie
  createdBy: string; createdAt; updatedAt;
};
```
`basen_enrollments` — dodać pole `slot: BasenSlotLabel`, dodać `type: "regular"|"training"|"instructor"`,
`instructorUid?: string|null`, `kayakId?: string|null` (sentinel `"PRIVATE"` lub id
z `gear_kayaks`). **ID dokumentu deterministyczne**: `${sessionId}_${slot}_${uid}` —
tworzone przez `.doc(id).set()`/`runTransaction` zamiast auto-ID, eliminuje race z
audytu (pkt 8, `basen_TO_DO.md`). Reużywalne jak w starej apce: jeśli dokument istnieje
ze `status!=="active"`, kolejny zapis go reaktywuje zamiast tworzyć duplikat.

Nowa kolekcja `basen_kayak_allocations/{id}`, ID deterministyczne `${sessionId}_${slot}_${kayakId}`:
`{sessionId, slot, kayakId, enrollmentId, uid, createdAt}`. Brak alokacji dla `kayakId==="PRIVATE"`.

**Funkcje do przepisania** (zachować istniejący styl transakcji Firestore z obecnego
`basen_service.ts:178-267/269-341/343-395`):
- `createSession(db, {date, h1, h2, sauna?, notes, createdBy})` — buduje `slots` z
  wartości formularza lub domyślnych z `getBasenVars()` (`basen_1_godzina_domyslna`,
  `basen_2_godzina_domyslna`, `basen_limit_uczestnikow`).
- `listUpcomingSessions(db)` — bez zmian koncepcyjnie, query `date>=today`, ale zwraca
  pełny dokument ze `slots`.
- `enrollInSlot(db, {sessionId, slot, uid, email, displayName, mode, instructorUid?, paymentType?, kayakId?})`:
  - `mode==="instructor"`: bez pobierania karnetu, `type:"instructor"`, walidacja roli/flagi
    instruktora **musi** być zrobiona w handlerze (patrz Faza C) przed wywołaniem.
  - `mode==="regular"|"training"`: transakcja `runTransaction` na `sessionRef` (odczyt
    `slots[slot]`, walidacja `status!=="cancelled"`, `enrolledCount<capacity`, dekrementacja
    karnetu jeśli `paymentType==="karnet"` — logika 1:1 z dzisiejszego `enrollInSession`),
    plus `tx.set(enrollmentRef, ...)` pod deterministycznym ID (odczyt+ewentualna reaktywacja
    w TEJ SAMEJ transakcji, zamiast osobnego query przed transakcją jak dziś — to usuwa
    wyścig z audytu).
  - Jeśli `kayakId` podany i `!== "PRIVATE"`: w tej samej transakcji `tx.get(allocationRef)` —
    jeśli istnieje, błąd „Ten kajak jest już zajęty dla tej godziny."; inaczej `tx.set(allocationRef, ...)`.
- `cancelEnrollment(db, {sessionId, slot, uid, cancellationWindowHours})` — znajduje
  dokument po deterministycznym ID zamiast `enrollmentId` z requestu (patrz Faza C, zmiana
  API), reszta logiki (okno czasowe, zwrot karnetu) jak dziś (`cancelEnrollment:269-341`).
  Dodatkowo: jeśli `kayakId` był ustawiony i `!=="PRIVATE"` — usunąć dokument alokacji.
- `cancelSession(db, sessionId, slot?)` — jeśli `slot` podany, anuluje tylko ten slot
  (ustawia `slots[slot].status="cancelled"`, anuluje zapisy tego slotu, zwraca karnety,
  sprząta alokacje kajaków); jeśli brak `slot`, pętla po wszystkich slotach dnia (wygodne
  „anuluj cały dzień"). Logika transakcji jak dziś (`cancelSession:343-395`), tylko
  sparametryzowana slotem.
- `listAvailableBasenKayaks(db, sessionId, slot)` — **nowa funkcja**: `gear_kayaks` gdzie
  `storedAt` (case-insensitive) `=="basen"` i `isOperational===true`, minus te już
  zaalokowane w `basen_kayak_allocations` dla `{sessionId,slot}` (osobne query, diff w
  pamięci — mała skala, nie trzeba łączonego indeksu). Zwraca listę + zawsze dokleja
  `{id:"PRIVATE", label:"Kajak prywatny"}` na końcu (wzorem starej apki, §5.7 specyfikacji).
- `addMeAsInstructor` / `removeMeAsInstructor` — de facto `enrollInSlot(mode:"instructor")` /
  `cancelEnrollment` na własnym uid, bez owijania w nową funkcję (frontend wywołuje te
  same dwa endpointy z `mode="instructor"`).
- `listSlotAttendees(db, sessionId, slot)` — **nowa funkcja**: jedno query `basen_enrollments`
  gdzie `sessionId==X, slot==Y, status=="active"` (wymaga nowego indeksu — patrz „Indeksy"
  niżej), grupowanie w pamięci po `type` na 3 kategorie (regular+training-bez-instruktora,
  training-z-instruktorem sparowane po `instructorUid`, instructor) — dokładnie wzorem
  `AttendeesList` starej apki (§5.8 specyfikacji), zaadaptowane bez sekcji „Sauna" osobno
  (bo to już jest jeden ze slotów, nie osobna kategoria).
- `getUserKarnety`/`getActiveKarnet`/`grantKarnet` — bez zmian.

**Usunąć całkowicie**: `functions/src/modules/basen/basen_godziny_service.ts`.
