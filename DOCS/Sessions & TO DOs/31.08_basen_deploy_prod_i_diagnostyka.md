## 1. Deploy na produkcję — trzy nieudane próby, czwarta udana

`firebase deploy` (`morzkulc-e9df7`) padał trzykrotnie z trzech różnych
przyczyn, każda naprawiona osobno:

### 1a. Nieprawidłowy indeks Firestore
`firestore.indexes.json` zawierał wpis dla `basen_sessions: date ASC` — pojedyncze
pole, które Firestore i tak indeksuje automatycznie. Firestore API odrzucił to
błędem `400: this index is not necessary, configure using single field index
controls`. **Naprawa**: usunięcie tego wpisu z pliku.

### 1b. Martwe funkcje blokujące deploy
Po przebudowie modułu w kodzie nie istniały już 4 stare funkcje „godzin
basenowych" (`basenAdminAddGodziny`, `basenAdminCorrectGodziny`,
`basenAdminSearchUsers`, `getBasenGodziny`), ale wciąż żyły na produkcji.
`firebase deploy` odmawia ich cichego skasowania w trybie nieinteraktywnym.
**Naprawa**: `firebase functions:delete basenAdminAddGodziny
basenAdminCorrectGodziny basenAdminSearchUsers getBasenGodziny --region
us-central1 --force` (za Twoją wyraźną zgodą).

### 1c. Zepsuty lockfile — `npm ci` w Cloud Build
Po naprawie 1b deploy padał w Cloud Build z `npm error EUSAGE: npm ci can only
install packages when your package.json and package-lock.json are in sync` —
brakujące/niespójne wpisy dla `@emnapi/core`, `@emnapi/runtime`,
`@emnapi/wasi-threads`. Pierwsza próba naprawy (`npm install` bez czyszczenia)
tylko częściowo załatała lockfile — kolejny deploy padł na innej wersji tych
samych pakietów. **Diagnoza**: `npm ls @emnapi/core` pokazał je jako
`extraneous` — obecne w `node_modules`, ale nieprzypisane w drzewie
zależności lockfile'a. **Prawdziwa naprawa**: pełne czyszczenie
(`rm -rf node_modules package-lock.json && npm install`) — po tym `@emnapi/*`
poprawnie wisi pod swoim realnym rodzicem (`firebase-functions-test` → `jest`
→ `unrs-resolver` → `@napi-rs/wasm-runtime`), build/lint czyste, deploy
przechodzi.

**Czwarta próba: sukces.** Firestore indexes + Functions (wszystkie, w tym 3
nowe: `basenSetKayak`, `getBasenKayaks`, `getBasenAttendees`) + Hosting —
wszystko wdrożone bez błędów.

## 2. Cloud Run invoker — 3 nowe funkcje wymagały ręcznego przełączenia

Zgodnie z wcześniejszym audytem projektu (`15.06_audyt_invoker_funkcje.md`),
świeżo utworzone funkcje HTTP powinny dostawać „Public access" w Cloud Run
automatycznie przy pierwszym deployu — **tym razem tak się nie stało**.

**Weryfikacja** (curl bez tokenu na żywy Hosting URL):
- Istniejące funkcje (`getSetup`, `registerUser`) → poprawnie `401
  {"error":"Missing token"}` (błąd na poziomie aplikacji — OK).
- 3 nowe funkcje basenowe → goły `403` bez treści (błąd na poziomie
  infrastruktury Cloud Run — invoker NIE jest publiczny).

Próba naprawy przez `gcloud run services add-iam-policy-binding` nie powiodła
się z dwóch niezależnych przyczyn: `gcloud` w Bash nie znajduje Pythona, a w
PowerShell komenda została zablokowana przez klasyfikator auto-mode (zmiana
IAM w produkcji wymaga jawnej zgody). **Ty ręcznie przełączyłeś** te 3 funkcje
na „Public access" w Cloud Console. Ponowna weryfikacja curlem potwierdziła
naprawę: wszystkie 3 endpointy odpowiadają teraz poprawnie na poziomie
aplikacji (`405 Method not allowed` dla `basen/kayak` na GET, `401 Missing
token` dla pozostałych dwóch).

**Wniosek do zapamiętania**: nie ufaj ślepo temu, że nowe funkcje HTTP dostają
publiczny invoker automatycznie — zawsze weryfikuj curlem po deployu.

## 5. Ograniczenie środowiska: brak weryfikacji Firestore z tej maszyny

Nie mam obecnie żadnego sposobu na bezpośredni odczyt danych z Firestore
(prod: `morzkulc-e9df7`) z tej maszyny:
- **Brak konektora** — w tej sesji nie jest podłączony żaden konektor
  Firestore/GCP (tylko Google Drive).
- **`gcloud` niedostępny** — nierozwiązany błąd weryfikacji certyfikatu SSL
  (błąd Pythona), próby obejścia przez zmienne środowiskowe
  (`CLOUDSDK_PYTHON`, `REQUESTS_CA_BUNDLE`, `SSL_CERT_FILE`,
  `CLOUDSDK_CA_CERTS_FILE`) nieskuteczne.
- **Brak lokalnego klucza service account** i brak Application Default
  Credentials (`%APPDATA%\gcloud\application_default_credentials.json` nie
  istnieje).
- `firebase functions:log` działa, ale zwraca fragmentaryczne/niepełne wyniki
  (nie da się nim niezawodnie prześledzić konkretnego zdarzenia w czasie) —
  niewystarczające jako substytut odczytu bazy.

**Rekomendowana trwała naprawa** (Twoja decyzja, do zrobienia kiedy
wygodnie): wygenerować w Cloud Console service account z rolą tylko-do-odczytu
(**Cloud Datastore Viewer** wystarczy), pobrać klucz JSON, podać mi ścieżkę
lokalnie (NIE commitować do gita). To odblokuje możliwość pisania małych,
bezpiecznych skryptów odczytu Firestore na żądanie, niezależnie od
kaprysów gcloud/gita.

Do tego czasu weryfikacja stanu danych w Firestore = ręczne sprawdzenie w
Firebase Console przez Ciebie, albo zaufanie wynikowi wyświetlonemu przez
panel admina po akcji.
