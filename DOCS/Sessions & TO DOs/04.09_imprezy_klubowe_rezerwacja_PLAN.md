# Kierownik imprezy klubowej — bezpłatne rezerwacje sprzętu na imprezę

## Kontekst

Klub organizuje część imprez z listy „Imprezy" samodzielnie (np. spływy, zawody), a część to
imprezy zaprzyjaźnionych klubów (Bystrze, Panta Rei, Habazie, Przewrotka) lub zewnętrzne, o
których tylko informujemy. Dla imprez organizowanych przez Morzkulc potrzebny jest **kierownik**
(dowolny członek lub kandydat), który — od momentu zatwierdzenia imprezy przez zarząd/KR aż do
jej zakończenia — może zarezerwować dowolną ilość sprzętu **bezpłatnie**, wyłącznie na potrzeby
tej imprezy. Taki sprzęt musi być widoczny w aplikacji jako zarezerwowany na imprezę klubową
(dla każdego przeglądającego, nie tylko dla kierownika). Dodatkowo, ponieważ klub działa w
grupie zaprzyjaźnionych klubów, chcemy na liście imprez wyróżniać ikonką, który z pięciu klubów
(Morzkulc + 4 partnerskie) jest organizatorem danej imprezy.

Dzisiejszy kod (`events` w Firestore, moduł `impreza_module.js`, panel zarządu) nie ma żadnego
pojęcia organizatora ani kierownika — jedyny ślad osoby to zgłaszający (informacyjny, bez
uprawnień). System rezerwacji sprzętu (`gear_reservations`, `gear_bundle_service.ts`) ma już
gotowy, sprawdzony mechanizm bezpłatnego wypożyczenia dla kursanta/kandydata w oknie
szkoleniówki (`feeExempt` → `waived:true`) — to naturalny wzorzec do rozszerzenia o trzeci
warunek zwolnienia: aktywny kierownik imprezy klubowej.

**Decyzje ustalone z użytkownikiem (ostateczne):**
1. Kierownika/organizatora można ustawić **dwoma kanałami**: formularz zgłoszenia imprezy w
   aplikacji (pole staje się wymagane, gdy organizator = Morzkulc) ORAZ arkusz Google (dwie nowe
   kolumny), z pełną synchronizacją dwukierunkową jak dziś dla nazwy/dat/opisu — czyli korekta w
   arkuszu (błędny e-mail, zły klub) zawsze nadpisuje bazę przy najbliższym syncu.
2. „Impreza klubowa" to **wyłącznie** impreza z `organizer === "morzkulc"` **i** ustawionym
   kierownikiem — pole liczone (computed), nie osobna flaga w bazie.
3. Przywilej kierownika aktywuje się **dopiero po zatwierdzeniu** imprezy (`approved:true`), nie
   przy samym zgłoszeniu — zabezpieczenie przed samodzielnym przyznaniem sobie darmowego sprzętu
   przed weryfikacją zarządu.
4. Jeden użytkownik może być aktywnym kierownikiem **tylko jednej** imprezy klubowej naraz —
   wymuszane przy zatwierdzaniu imprezy i przy korekcie kierownika już zatwierdzonej imprezy przez
   sync arkusza.
5. Termin rezerwacji „na imprezę klubową" = zawsze daty imprezy + standardowy offset odbioru/
   zwrotu (bez ręcznego wyboru dat przez kierownika).
6. UI nie pyta, na którą imprezę — jest zawsze co najwyżej jedna aktywna naraz. Widoczność dla
   innych: „Impreza klubowa — kierownik: {ksywka/nazwisko}" (bez nazwy imprezy).
7. Pole „Organizator" to zamknięta lista 5 kluby (Morzkulc/Bystrze/Panta Rei/Habazie/Przewrotka);
   brak wyboru = brak ikonki/informacji. Ikonki na liście imprez dla wszystkich 5 (Morzkulc też).
8. Loga: Bystrze, Panta Rei i Habazie — gotowe pliki (Habazie: czarna grafika na przezroczystym
   tle, zwykłe zmniejszenie jak pozostałe). Przewrotka — tylko PDF, szeroki czarny wordmark (nie
   plakietka), wymaga konwersji+kadrowania. Placeholder tam, gdzie potrzebny, z możliwością
   podmiany pliku bez zmian w kodzie.

## 1. Model danych

**`events`** — nowe pola (`functions/src/modules/calendar/events_service.ts`, typ `EventRecord`):
- `organizer: string` — `""` lub jeden z `"morzkulc"|"bystrze"|"panta_rei"|"habazie"|"przewrotka"`.
- `kierownikEmail: string` — tylko istotne gdy `organizer==="morzkulc"`, inaczej wymuszone `""`.
- `kierownikUid: string | null`
- `kierownikDisplayName: string` — zdenormalizowane (ksywka → imię+nazwisko → e-mail), żeby
  listy imprez nie potrzebowały dodatkowego odczytu.

Impreza klubowa = `organizer === "morzkulc" && !!kierownikUid` (liczone, nie zapisywane).

**`gear_reservations`** — nowe pole (`gear_bundle_service.ts`):
- `eventId: string | null` — jedyny dyskryminator; `schoolYear` zostaje wyłącznie dla zwolnienia
  szkoleniówkowego (gdy `eventId` ustawione, `schoolYear` zawsze `null`).

**`godzinki_ledger`** (spend, opcjonalnie ale zalecane) — `eventId?: string|null` na
`writeWaivedSpendInTx`/`GodzinkiRecord`, żeby historia godzinek też odróżniała powód zwolnienia.

**Nowy indeks Firestore** (`firestore.indexes.json`) — zapytanie „aktywna impreza kierownika":
```json
{
  "collectionGroup": "events",
  "queryScope": "COLLECTION",
  "fields": [
    { "fieldPath": "kierownikUid", "order": "ASCENDING" },
    { "fieldPath": "approved", "order": "ASCENDING" },
    { "fieldPath": "endDate", "order": "ASCENDING" }
  ]
}
```
Wdrożyć (`firebase deploy --only firestore:indexes`) **przed** kodem, który tego zapytania używa.

## 2. Backend

### `functions/src/modules/calendar/events_service.ts`
- `EVENT_ORGANIZER_KEYS` (5 kluczy) + `isValidOrganizerKey()`.
- `resolveKierownikCandidate(db, email, memberRoleKeys)` — szuka w `users_active` po e-mailu,
  wymaga roli w `memberRoleKeys`, buduje `displayName` (ksywka→imię+nazwisko→email). Współdzielone
  przez `createEvent` i sync z arkusza.
- `findActiveKierownikEvent(db, uid, todayIso?)` — query po nowym indeksie, filtr `rejected!==true`
  w pamięci (wzorem `listUpcomingEvents`).
- `findActiveKierownikConflict(db, kierownikUid, excludeEventId?, todayIso?)` — jak wyżej, z
  wykluczeniem bieżącej imprezy.
- `createEvent(...)` — nowe argumenty `organizer`, `kierownikEmail`, `memberRoleKeys`; walidacja:
  organizator musi być z listy 5 (albo pusty); jeśli `"morzkulc"` → `kierownikEmail` wymagany +
  `resolveKierownikCandidate` (błąd `kierownik_not_found` jeśli nie rozwiąże); jeśli inny/pusty →
  wymuś `kierownikEmail=""/kierownikUid=null/kierownikDisplayName=""`. **Brak** sprawdzenia
  konfliktu „jeden kierownik naraz" tutaj — to sprawdzane dopiero przy zatwierdzeniu (decyzja #3/#4).

### `functions/src/api/submitEventHandler.ts`
Odczytaj `organizer`/`kierownikEmail` z body, przekaż do `createEvent` razem z
`deps.memberRoleKeys` (już dostępne).

### `functions/src/service/tasks/eventsSyncFromSheet.ts`
- Nowe kolumny arkusza: **„Organizator"** i **„Kierownik (e-mail)"** — użytkownik musi je dodać w
  zakładce „imprezy". Odczyt case/spacing-insensitive (istniejący wzorzec `canonicalHeader`).
- `parseOrganizerFromSheetCell(raw)` — tolerancyjne dopasowanie do 5 kluczy (lowercase, bez
  diakrytyków/spacji); nierozpoznana wartość → `organizer=""` + log + licznik
  `organizerUnrecognized` (bez przerywania syncu całej reszty wiersza).
- Gdy `organizer!=="morzkulc"` → wymuś puste pola kierownika.
- Gdy `organizer==="morzkulc"` i podano e-mail → `resolveKierownikCandidate`; błąd → zostaw
  `kierownikEmail` (do wglądu), ale `kierownikUid=null` (więc „impreza klubowa" liczy się jako
  false) + licznik `kierownikResolutionFailed`.
- **Guard konfliktu**: jeśli impreza jest już `approved===true` i nowo rozwiązany `kierownikUid`
  się zmienia względem obecnego → `findActiveKierownikConflict`; jeśli konflikt → **pomiń**
  wyłącznie pola organizator/kierownik w tym patchu (reszta pól wiersza syncuje się normalnie),
  log + licznik `kierownikConflictsSkipped`.
- `buildEventRowPatch` — dopisz `"Organizator"`/`"Kierownik (e-mail)"` do zapisywanego wiersza.
  **Nie** dodawać do `EVENT_ROW_CREATE_ONLY_COLUMNS` (te dwie kolumny mają być zawsze nadpisywane
  z arkusza przy syncu — inaczej niż `Zatwierdzona`/`ranking?`/`kursowa?`, które są chronione tylko
  w kierunku zapisu aplikacja→arkusz, nie czytania arkusz→baza).
- Liczniki `organizerUnrecognized`/`kierownikResolutionFailed`/`kierownikConflictsSkipped`
  dopisane do komunikatu wyniku syncu (wzorem istniejących `backfilled`/`confirmedInSheet`).

### `functions/src/api/adminApprovalHandler.ts` (`handleAdminApprove`, kind="event")
Przed zapisem `approved:true`: jeśli `organizer==="morzkulc" && kierownikUid` →
`findActiveKierownikConflict`; konflikt → **409** `kierownik_already_assigned` z czytelnym
komunikatem („Wskazany kierownik jest już kierownikiem innej aktywnej imprezy klubowej
(„{nazwa}”, do {data}). Zmień kierownika lub poczekaj, aż tamta się zakończy.") — front nie
wymaga zmian, `mapUserFacingApiError` już przepuszcza nieznane kody z serwerowym `message`.

### `functions/src/api/getAdminPendingHandler.ts`
Dopisz `organizer`/`kierownikEmail`/`kierownikDisplayName` do `eventsItems`, żeby zarząd widział
przypisanie przed kliknięciem „Zatwierdź" (unika niespodziewanego 409).

### `functions/src/modules/equipment/bundle/gear_bundle_service.ts`
- `createBundleReservation` — nowy arg `asClubEvent?: boolean` + `memberRoleKeys: string[]`
  (z `deps`). Gdy `true`:
  - odrzuć jeśli rola spoza `memberRoleKeys` (obrona w głąb);
  - `findActiveKierownikEvent(db, uid)` — brak → `not_a_kierownik`;
  - **nadpisz** `startDate/endDate` datami imprezy (ignoruj to, co przyśle klient — decyzja #5),
    ustaw `eventId`;
  - **pomiń całkowicie**: `roleMaxWeeks`/horyzont, `maxReservationLengthDays`,
    `roleMaxItems`/`findCategoryOverLimit` per kategoria (decyzja „dowolna ilość");
  - **nigdy nie pomijaj**: `fetchItemDetails` (sprawność/basen/zgoda właściciela) i
    `findBundleConflicts` (konflikt terminów) — bez zmian, chronią przed podwójną rezerwacją.
  - `feeExempt = exempt || boardFeeExempt || Boolean(eventId)`; `schoolYear` wymuszone `null` gdy
    `eventId` ustawione (decyzja #9 — rozróżnienie etykiety).
  - zapis dokumentu: `eventId`, `waived` jak dziś liczone.
  - odpowiedź: dopisz `eventId` (frontend rozróżnia komunikat sukcesu).
- `updateBundleReservationDates` — na starcie: jeśli `r.eventId` ustawione → odrzuć zmianę dat
  (`club_event_reservation_locked`, komunikat: „Terminy rezerwacji na imprezę klubową są ustalane
  automatycznie na podstawie dat imprezy. Anuluj i zarezerwuj ponownie, jeśli daty imprezy się
  zmieniły."). Anulowanie (`cancelReservation`/`adminCancelReservation`) — **bez zmian**, działa
  identycznie (weryfikacja: `adminCancelReservation` na rezerwacji `waived` już dziś bezpiecznie
  nie odzyskuje niczego z FIFO, sam refund jest no-opem na saldzie).

### `functions/src/api/gearBundleReservationCreateHandler.ts`
Odczytaj `asClubEvent` z body; waliduj daty tylko gdy `!asClubEvent`; przekaż `asClubEvent` +
`deps.memberRoleKeys` do `createBundleReservation`.

### `functions/src/api/getKayakReservationsHandler.ts`
Dopisz `isClubEvent: Boolean(r?.eventId)` do każdej pozycji odpowiedzi (bez nazwy imprezy — tylko
flaga, zasila kalendarz zajętości i listę „Więcej").

### `functions/src/api/registerUserHandler.ts` + `index.ts`
Dopisz `memberRoleKeys` do zależności handlera (już dostępne w `index.ts`). Dla użytkownika w
`memberRoleKeys`: `findActiveKierownikEvent` → w odpowiedzi `/api/register`:
`isActiveKierownik: boolean`, `activeKierownikRange: {startDate, endDate} | null` (tylko daty,
bez nazwy imprezy — front pokazuje checkbox + zablokowany zakres dat bez dodatkowego fetcha).

### `functions/src/modules/hours/godzinki_service.ts` / `getGodzinkiHandler.ts` (opcjonalnie, zalecane)
`writeWaivedSpendInTx` — dodaj opcjonalny `eventId` (w pełni wsteczne kompatybilne, istniejące
wywołania nic nie przekazują → `null`). `serializeRecord` — dopisz `eventId` do wyniku spend.

## 5. Ryzyka i przypadki brzegowe

- **Cofnięcie zatwierdzenia po tym, jak sprzęt już zarezerwowano** — istniejące rezerwacje NIE są
  automatycznie anulowane/przeliczane (spójne z tym, jak działa dziś zwolnienie szkoleniówkowe).
  Zarząd musi ręcznie anulować przez istniejący panel, jeśli to konieczne.
- **Wyścig przy weryfikacji „jeden kierownik naraz"** — sprawdzenie przy zatwierdzeniu i przy
  syncu arkusza nie jest transakcyjne; teoretyczny wyścig między równoczesnym zatwierdzeniem a
  syncem jest przyjęty jako znikome ryzyko (rzadkie, ręczne akcje), nie dodajemy blokady
  transakcyjnej.
- **Kandydat będący jednocześnie w oknie szkoleniówki i kierownikiem imprezy** — `eventId` ma
  pierwszeństwo nad `schoolYear` przy etykietowaniu; nie ma podwójnego zwolnienia (jeden zapis
  `writeWaivedSpendInTx`).
- **Testy regresyjne do zaktualizowania**: `tests/test_bundle_reservations.py` (nowe scenariusze:
  bypass limitów, wymuszone daty, `not_a_kierownik`, konflikty nadal wykrywane) oraz
  `functions/test/events_core.test.ts` (`buildEventRowPatch` — nowe kolumny;
  `EVENT_ROW_CREATE_ONLY_COLUMNS` — bez zmian, nowe pola tam NIE trafiają).

## 7. Weryfikacja

1. `npm --prefix functions run build` + `npm --prefix functions run lint` + `npm --prefix functions run test`.
2. `pytest tests/test_bundle_reservations.py` po dopisaniu nowych scenariuszy.
3. Ręcznie na prod (`morzkulc-e9df7.web.app`):
   - Zgłoszenie imprezy z organizatorem Morzkulc bez kierownika → błąd walidacji.
   - Zgłoszenie z kierownikiem → widoczne w panelu zarządu z organizatorem/kierownikiem.
   - Próba zatwierdzenia drugiej imprezy z tym samym aktywnym kierownikiem → 409 z czytelnym
     komunikatem.
   - Po zatwierdzeniu: kierownik widzi checkbox „Rezerwuję na imprezę klubową" w module Sprzęt,
     daty zablokowane na zakres imprezy, dowolna liczba przedmiotów, koszt zwolniony.
   - Inny użytkownik przeglądający ten sprzęt widzi „Impreza klubowa — kierownik: {nazwa}" w
     szczegółach i w tooltipie kalendarza zajętości.
   - Korekta błędnego e-maila kierownika w arkuszu → po syncu poprawnie odzwierciedlona w bazie
     i w aplikacji.
   - Ikony 5 klubów widoczne na liście imprez i widgecie strony głównej, brak ikonki gdy
     organizator nie wybrany.
4. Deploy: `firebase deploy --only functions,hosting,firestore:indexes`.
