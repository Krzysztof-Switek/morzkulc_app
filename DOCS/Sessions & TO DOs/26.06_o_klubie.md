# 26.06 — Box „Klub" w panelu użytkownika (analiza + plan)

## Cel

Rozbudować sekcję użytkownika (panel profilu otwierany kliknięciem w ikonę
ludzika na górze strony, trasa `#/home/profile`) o dodatkowy **box „Klub"** z
ogólnymi informacjami klubowymi w jednym miejscu:

- numer konta klubowego + bank,
- osoby z zarządu (funkcje),
- komisja rewizyjna (KR),
- (docelowo) kto ma klucze do klubu,
- (docelowo) linki do regulaminów i statutu.

**Kluczowa obserwacja:** te dane **już istnieją** w Firestore (synchronizowane z
arkusza Google). Nie tworzymy nowego modelu wprowadzania danych — jedynie je
**porządkujemy i prezentujemy** w jednym miejscu.

---

## Co znalazłem (analiza kodu)

### 1. Panel profilu — gdzie się renderuje

- Przycisk ludzika: `public/index.html:30` (`#profileBtn`), handler w
  `public/core/app_shell.js:70` → `location.hash = "#/home/profile"`.
- Główna funkcja renderująca: **`renderHomeProfile()`** w
  `public/core/render_shell.js:422–625`.
- Struktura panelu: karta profilu (`profileCard`) z „chipami" (Rola, Status,
  Składki/Wpisowe, Saldo godzinek), opcjonalny pasek dla kursanta, bloki stażu i
  opiekunów dla kandydata (`profileBlock`/`profileBlockTitle`), sekcja „Moje
  rezerwacje" (tylko `canReserveGear`).
- **Wzorzec leniwego ładowania:** panel renderuje placeholdery, a potem dociąga
  dane async — `/api/godzinki?view=home` (linia 568) i `/api/km/kursant-stats`
  (linia 606). Nasz box „Klub" pójdzie dokładnie tym wzorcem.
- Flagi ról dostępne przez `getDashboardConfig(ctx)`
  (`render_shell.js:96`): `isKursant`, `isSympatyk`, `isKandydat`,
  `canReserveGear`, `isAdmin` itd.

### 2. Routing API

Każda ścieżka `/api/*` to osobny **rewrite Hostingu → nazwana Cloud Function**
w `firebase.json` (`hosting.rewrites`, np. `/api/setup` → `getSetup`,
linie 98–103). Czyli `/api/klub` wymaga nowego rewrite + nowej funkcji.

### 3. Model danych klubowych (już istnieje)

| Dane | Lokalizacja w Firestore |
|---|---|
| Funkcje zarządu: email operatora + skrzynka funkcyjna | `service_state/function_roles.{prezes,skarbnik,sprzetowiec,szkoleniowiec}` → `{email, mailbox}` |
| Fallback emaila funkcji | `setup/vars_members.vars.<rola>.value` |
| Imię + nazwisko operatora | `users_active` (lookup po `email`) → `profile.firstName` + `profile.lastName` |
| Konto klubowe / bank | `setup/vars_members.vars.konto_klubowe.value`, `…bank_klubowy.value` (grupa „finanse") |
| Komisja rewizyjna (KR) | `users_active` gdzie `role_key == "rola_kr"` |
| Statut / regulamin / klucze | *(jeszcze brak)* — przyszłe zmienne SETUP (`statut_url`, `regulamin_url`, `klucze`) |

Przykład danych z arkusza (zakładka SETUP, kolumny: zmienna / wartość / grupa):

```
sprzetowiec     switek.k@gmail.com              role
szkoleniowiec   zwirowski@gmail.com             role
prezes          gordziej.mateusz@gmail.com      role
skarbnik        katastrofalnydeszcz@gmail.com   role
konto_klubowe   19187010452078108328610001      finanse
bank_klubowy    Nest                            finanse
```

Te zmienne lądują w `setup/vars_members.vars` jako
`{ [nazwa]: { type, value, group, description } }` — patrz task synchronizujący
`functions/src/service/tasks/setupSyncFromSheet.ts` (`readSetupVars`,
linie 175–203; zapis do `setup/vars_members`, linia 254). **Wartości w grupie
„role" to maile**, nie nazwy — trzeba je rozwiązać do imienia i nazwiska.

### 4. Gotowy wzorzec do reużycia (email → nazwa)

`resolveSzkoleniowiec()` w `functions/src/api/registerUserHandler.ts:370–409`
robi dokładnie to, czego potrzebujemy dla każdej funkcji:

1. czyta `service_state/function_roles.szkoleniowiec.{email, mailbox}`,
2. fallback do `setup/vars_members.vars.szkoleniowiec.value`,
3. rozwiązuje email → `users_active.profile.firstName + lastName`,
4. **kontakt zawsze przez skrzynkę funkcyjną** (`mailbox`), nie prywatny adres.

Uogólnimy go na 4 funkcje. Skrzynki funkcyjne są w
`service_config.functionRoles.<rola>.mailbox` (`functions/src/service/service_config.ts:84`).

### 5. Role / KR

W mapowaniu ról (`setupSyncFromSheet.ts:26–33`) `rola_kr` ma etykietę „KR"
(komisja rewizyjna). Lista KR = zapytanie `users_active where role_key ==
"rola_kr"` (wzorzec zapytania po roli: `getKursantStatsHandler.ts`).

## Decyzje (uzgodnione z użytkownikiem)

- **Źródło danych:** istniejące dokumenty Firestore (NIE tworzymy `setup/app.klub`).
- **Zarząd:** prezentujemy istniejącą listę funkcji (prezes, skarbnik,
  sprzętowiec, szkoleniowiec) + KR z ról użytkowników.
- **Widoczność boxa:** **wszyscy zalogowani** (każda rola, łącznie z kursantem i
  sympatykiem).
- **Zakres startowy:** zarząd + KR + konto/bank. Statut/regulamin/klucze pojawią
  się automatycznie po dodaniu odpowiednich zmiennych do arkusza SETUP.

## Plan implementacji

### Architektura
Nowy, **leniwie ładowany** endpoint `GET /api/klub` + nowa sekcja „Klub" w
`renderHomeProfile`, pobierana po renderze (jak `/api/godzinki?view=home`).

### Backend

1. **Nowy handler** `functions/src/api/getKlubInfoHandler.ts` (wzorzec
   wstrzykiwania `deps`, jak inne pliki w `api/`):
   - Auth: `requireIdToken` — każdy zalogowany (bez ograniczeń roli).
   - **Zarząd:** 1 odczyt `service_state/function_roles` + 1 odczyt
     `setup/vars_members`. Dla 4 funkcji ustal email operatora (state →
     fallback var). Nazwy rozwiąż **jednym** zapytaniem
     `users_active where email in [<=10]` (mapa email→nazwa). Kontakt =
     skrzynka funkcyjna (`mailbox`), nigdy prywatny email.
   - **KR:** `users_active where role_key == "rola_kr"` → nazwy z
     `profile.firstName/lastName` (fallback `nickname`/`displayName`), sort po
     nazwisku.
   - **Finanse:** `konto_klubowe`, `bank_klubowy` z `vars_members.vars`.
   - **Linki:** dołącz `statut_url` / `regulamin_url` / `klucze` jeśli istnieją.
   - Odpowiedź:
     `{ ok, zarzad:[{funkcja,name,mailbox}], kr:[{name}], finanse:{konto,bank}, linki:{statut?,regulamin?,klucze?} }`.
   - Etykiety: Prezes, Skarbnik, Sprzętowiec, Szkoleniowiec (w tej kolejności);
     funkcję bez operatora pomiń.
   - CORS + allowlist hosta jak `getSetup`.

2. **`functions/src/index.ts`:** eksport
   `export const getKlubInfo = onRequest({invoker:"private"}, (req,res)=>handleGetKlubInfo(req,res,{…deps}))`
   — reuse middleware (`sendPreflight`, `requireAllowedHost`, `setCorsHeaders`,
   `corsHandler`, `requireIdToken`, `db`).

3. **`firebase.json`:** rewrite `/api/klub` → `getKlubInfo` (region
   `us-central1`).

### Frontend

1. **`public/core/render_shell.js` → `renderHomeProfile()`:**
   - Po karcie profilu dodać `<section class="card center startSection klubBox">`
     z nagłówkiem „Klub" i placeholderem `#klubBoxBody` (`spinnerHtml(...)`).
     Renderowana **zawsze** (widoczna dla wszystkich).
   - Po renderze `apiGetJson({url:"/api/klub", idToken})` i zbudować bloki
     (każdy ukrywany, gdy brak danych):
     - **Zarząd** — wiersze `funkcja → nazwa` + `mailto:` do skrzynki funkcyjnej
       (reuse `mentorRow`/`mentorRole`/`mentorName`).
     - **Komisja rewizyjna** — lista nazwisk (gdy `kr.length`).
     - **Konto klubowe** — bank + numer w grupach
       (`19 1870 1045 2078 1083 2861 0001`) + przycisk „Kopiuj".
     - **Dokumenty** — linki Statut / Regulamin (gdy obecne); „Klucze" jako
       tekst, gdy zmienna istnieje.
   - Wartości przez `escapeHtml`. Błąd → „Nie udało się pobrać informacji
     klubowych."
   - (Opcjonalnie) cache w `sessionStorage` ~15 min (wzorem
     `_ADMIN_BADGE_CACHE_*`).

2. **`public/styles/start.css`:** style dla `klubBox`, wiersza konta i przycisku
   „Kopiuj", spójne z `profileBlock`/`mentorRow`/`startStatChip`.

### Helper
Mały helper w `render_shell.js`: numer NRB (26 cyfr) → grupy „2 + 6×4"; surowa
wartość do kopiowania.

### Pliki do zmiany / utworzenia
- **nowy** `functions/src/api/getKlubInfoHandler.ts`
- `functions/src/index.ts` — eksport `getKlubInfo`
- `firebase.json` — rewrite `/api/klub`
- `public/core/render_shell.js` — sekcja „Klub"
- `public/styles/start.css` — style boxa

### Reużycie
- `resolveSzkoleniowiec()` (`registerUserHandler.ts:370`) → uogólnić na 4 funkcje.
- `service_config.functionRoles.<rola>.mailbox` — skrzynki funkcyjne.
- Middleware z `index.ts` (jak `getSetup`).
- Front: `apiGetJson`, `escapeHtml`, `spinnerHtml`, klasy `profileBlock`/`mentorRow`.

## Weryfikacja

1. `npm --prefix functions run lint && npm --prefix functions run build`.
2. Lokalnie `npm --prefix functions run serve` **lub** deploy na dev:
   `firebase use dev` → `firebase deploy --only functions:getKlubInfo,hosting`.
3. Ludzik → profil → box „Klub":
   - Zarząd: Prezes Mateusz Gordziej, Skarbnik …, Sprzętowiec (switek.k),
     Szkoleniowiec … — z `mailto:` do skrzynek funkcyjnych.
   - KR: lista z `rola_kr`.
   - Konto: `19 1870 1045 2078 1083 2861 0001`, bank „Nest", „Kopiuj" działa.
4. Widoczność dla różnych ról (sympatyk, kursant, członek) — box widać dla
   wszystkich.
5. `GET /api/klub` bez tokenu → 401.
6. **Po deployu** (zgodnie z `reference_function_invoker_state`): potwierdź, że
   invoker Cloud Run `getKlubInfo` jest **publiczny** (jak inne `/api/*`), inaczej
   403; autoryzację i tak wymusza token w kodzie.

> Uwaga: wdrożenie to osobny, ręczny krok (jak poprzednie poprawki „NIE wdrożone").

## Rozszerzalność (statut / regulamin / klucze)
Aby dodać linki/klucze: dopisać wiersze w zakładce **SETUP** arkusza members
(np. `statut_url`, `regulamin_url`, `klucze`), zsynchronizować
(`setup.syncFromSheet`). Endpoint i box pokażą je automatycznie — **bez zmian w
kodzie** dla prostych wartości tekstowych/linków.
