## 3. Weryfikacja po wdrożeniu (probing przez prod Hosting)

Metoda: nieautoryzowany request na endpoint przez `https://morzkulc-e9df7.web.app` (PowerShell `Invoke-WebRequest` — używa magazynu certyfikatów Windows; `curl`/Git Bash i `gcloud` mają na tej maszynie problem z certyfikatem korporacyjnym → nie nadają się do probingu).

| Endpoint | Wynik | Interpretacja |
|---|---|---|
| `GET /api/admin/pending` (POST) | 405 | ✅ funkcja działa (GET-only → POST=405); zmiany Fazy 1 panelu live |
| `POST /api/admin/events/sync-calendar` | 401 | ✅ istniejąca funkcja, request dociera do handlera |
| `POST /api/events/submit` | 401 | ✅ kontrola — handler osiągany |
| **`POST /api/admin/approve`** | **403** | ⚠️ Cloud Run blokuje PRZED handlerem |
| **`POST /api/admin/reject`** | **403** | ⚠️ j.w. |
| `GET /api/admin/approve` | 403 | potwierdza: gdyby handler był osiągany, byłoby 405 (nie 403) → blokada na poziomie IAM, nie kodu |

**Wniosek**: kod jest poprawny (te same wzorce zwracają 401 na starszych funkcjach). Dwie **nowe** funkcje nie mają nadanego `roles/run.invoker` dla agenta Firebase Hosting na swoim serwisie Cloud Run.

## 4. 🔴 BLOKER — invoker dla nowych funkcji (do naprawy)

**Objaw**: `POST /api/admin/approve` i `/api/admin/reject` → 403. Przyciski **Zatwierdź/Odrzuć w panelu nie zadziałają** dopóki to wisi.

**Przyczyna**: przy wywołaniu prywatnej funkcji v2 (Cloud Run) przez rewrite Hostingu wymagane jest `roles/run.invoker` dla agenta Hostingu na serwisie Cloud Run. `firebase deploy` nadaje to dla NOWO tworzonych funkcji — ale gdy funkcja już istnieje, kolejny deploy traktuje ją jako „bez zmian" i POMIJA krok IAM. Dlatego ponowny `firebase deploy` nie naprawił 403.

**Fix (w zalogowanym terminalu użytkownika) — opcja A (pewna, zalecana)**: usunąć i wdrożyć ponownie, by firebase potraktował funkcje jako nowe i nadał invoker:
```
firebase functions:delete adminApprove adminReject --region us-central1 --force
firebase deploy --only functions,hosting
```
Usunięcie jest bezpieczne — funkcje są nowe, bez innych wywołań.

**Fix — opcja B (bez usuwania, przez gcloud)**: nadać invoker ręcznie (ten sam binding, który mają już działające funkcje):
```
PN=$(gcloud projects describe morzkulc-e9df7 --format='value(projectNumber)')
for f in adminApprove adminReject; do
  gcloud run services add-iam-policy-binding $f \
    --region=us-central1 --project=morzkulc-e9df7 \
    --member="serviceAccount:service-$PN@gcp-sa-firebasehosting.iam.gserviceaccount.com" \
    --role=roles/run.invoker
done
```

**Kryterium sukcesu**: po naprawie oba endpointy zwracają **401** zamiast 403 (request dociera do handlera, brak tokenu).

**Uwaga**: digest (scheduler), write-back i pass kalendarza NIE idą przez Hosting → są nietknięte tym blokerem i już działają. Bloker dotyczy wyłącznie ścieżki HTTP approve/reject z panelu.
