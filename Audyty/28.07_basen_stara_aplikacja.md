# Prompt dla nowej sesji Claude — moduł „Zapisy na basen (Morzkulc)”

Ten dokument jest **specyfikacją funkcjonalną** modułu zapisów, wyabstrahowaną z istniejącej aplikacji `basen-morzkulc-starter` (React + Vite + Firebase). Zawiera wyłącznie zachowania i reguły faktycznie zaimplementowane w kodzie źródłowym. Ma służyć jako brief do zaimplementowania tej samej funkcjonalności od zera w innym, większym projekcie — bez przenoszenia obecnego kodu (który ma błędy strukturalne i braki).

Traktuj poniższy tekst jako źródło prawdy o wymaganiach. Jeżeli w Twoim projekcie musisz odejść od któregoś rozwiązania (np. użyć innego backendu niż Firestore), zachowaj **zasady biznesowe** i model danych; strukturę techniczną możesz zaadaptować.

---

## 1. Domena i cel

Aplikacja do zapisów na cotygodniowe godziny basenowe kajakowe (grupa Morzkulc). W jednym dniu odbywają się dwie „godziny basenowe” (H1, H2) i opcjonalnie sauna. Uczestnicy mogą się zapisać zwykle, zapisać się z instruktorem (szkolenie), lub — jeśli mają rolę instruktora — dodać się jako dostępny instruktor. Do zapisu przypisywany jest kajak z inwentarza (albo „kajak prywatny”). Uczestnik płaci za pakiet godzin („credits”, „wykupione”, „godzinki”); każda rezerwacja pobiera 1 kredyt, wypisanie >24h zwraca 1 kredyt.

Domyślna lokalizacja terminu (podpowiedź w formularzu):
`Relaxcenter – Hotel Mercure Gdynia Centrum, Armii Krajowej 22, Gdynia`.

## 2. Model danych (kolekcje)

Wszystkie kolekcje są dokumentowe (obecnie Firestore). W nowym projekcie użyj równoważnika (Firestore/Postgres/etc.) — istotny jest kształt i inwarianty.

### 2.1 `users/{uid}`
Tworzony automatycznie przy pierwszym zalogowaniu, jeżeli nie istnieje:
```
uid: string
email: string | null
displayName: string | null
credits: number                 // domyślnie 0
status: 'pending' | 'active' | 'archived'   // start: 'pending'
roles: { admin: bool, organizer: bool, instructor: bool }   // start: wszystkie false
membership: { skkMorzkulcPaid: bool, zabikrukPaid: bool, jarmolowiczGroup: bool } // start: wszystkie false
createdAt: timestamp
// pola dopisywane akcjami:
statusUpdatedAt, rolesUpdatedAt, creditsPatchedAt
lastRefundBookingId, lastRefundAt
teachCredits: { [teachKey: string]: true }   // rejestr odebranych +1 za szkolenie
lastInstructorTeachAt
```

### 2.2 `pools/{poolId}` — terminy (dni basenowe)
```
date: 'YYYY-MM-DD'
location: string   // domyślnie DEFAULT_LOCATION (Relaxcenter)
hours: [
  { label: 'H1', start: 'HH:MM', end: 'HH:MM', capacity: number, trainingSlots: number },
  { label: 'H2', start: 'HH:MM', end: 'HH:MM', capacity: number, trainingSlots: number }
]
saunaEnabled: boolean
createdAt: timestamp
```
Domyślne wartości w formularzu admina:
H1 21:00–21:45, H2 21:45–22:30, capacity=12, trainingSlots=4, saunaEnabled=false.

### 2.3 `bookings/{bookingId}`
**Deterministyczne ID (kluczowy inwariant): `b_{poolId}_{hour}_{uid}`** — gwarantuje maks. jeden rekord na kombinację (użytkownik × termin × godzina). Reużywalne: jeżeli booking istnieje z `status != 'active'`, kolejny zapis go „reaktywuje” (update na `status='active'` + nowy typ + `createdAt=now`).
```
poolId, hour ('H1' | 'H2' | 'SAUNA'), uid
date: 'YYYY-MM-DD'
startAt: Date (data + godzina startu)
status: 'active' | 'cancelled' | 'cancelled_admin'
type: 'regular' | 'training' | 'instructor' | 'sauna'
userName: string   // displayName || email || 'Uczestnik'/'Instruktor'
userPublicRole: string  // wyliczana etykieta (patrz §3.3)
instructorUid: string | null   // ustawiane dla type='training'
kayakId: string | null         // 'PRIVATE' lub id z kolekcji kayaks, lub null
createdAt: serverTimestamp
cancelledAt: serverTimestamp   // po wypisie
```

### 2.4 `kayaks/{kayakId}`
```
name: string
note: string
active: boolean   // true = pokazywany na liście wyboru
createdAt: serverTimestamp
```
Specjalne, wirtualne „ID” do oznaczenia własnego kajaka: **`PRIVATE`** (stała `PRIVATE_KAYAK_ID`). Nie jest to dokument w kolekcji — nie tworzy alokacji i nie blokuje puli.

### 2.5 `allocations/{allocId}` — przydział kajaka na godzinę
**Deterministyczne ID (kluczowy inwariant, zapewnia unikalność kajaka w danym slocie): `alloc_{poolId}_{hour}_{kayakId}`**.
```
poolId, hour, kayakId
bookingId, uid
createdAt: serverTimestamp
```
Alokacje NIE są tworzone dla `PRIVATE`.

## 3. Uwierzytelnianie i uprawnienia

### 3.1 Logowanie
- Firebase Authentication, provider Google.
- `signInWithRedirect` (nie popup), `getRedirectResult` obsługiwany przy starcie.
- Persistencja: `browserLocalPersistence` (trwała sesja).
- Provider ustawiony z `custom_parameters: { prompt: 'select_account' }`.
- Wyjście: `signOut`.
- Po zalogowaniu subskrybowany jest własny dokument `users/{uid}` przez `onSnapshot`.

### 3.2 Statusy konta
- Nowe konto: `status='pending'`.
- **Tylko `status='active'` może się zapisywać.** Klient blokuje z komunikatem: „Twoje konto czeka na akceptację przez admina.” UI pokazuje baner `Twoje konto ma status: <status>. Admin musi je zatwierdzić...`.
- Admin może przełączać status w: `active`, `archived`, `pending` (dopisywany `statusUpdatedAt`).

### 3.3 Role i etykieta publiczna
Role (boolean, niezależne): `admin`, `organizer`, `instructor`. Członkostwa: `skkMorzkulcPaid`, `zabikrukPaid`, `jarmolowiczGroup`.

Etykietę `userPublicRole` (pokazywaną w rezerwacji) wylicza się w tej kolejności priorytetu (pierwszy true wygrywa):
1. `roles.instructor` → `"Instruktor"`
2. `roles.organizer` → `"Organizator"`
3. `roles.admin` → `"Admin"`
4. `membership.skkMorzkulcPaid` → `"SKK (składka)"`
5. `membership.zabikrukPaid` → `"Żabi Kruk (składka)"`
6. `membership.jarmolowiczGroup` → `"Grupa MJ"`
7. w przeciwnym razie → `"Gość"`

### 3.4 Reguły bezpieczeństwa (odzwierciedlenie logiki serwerowej)
Model uprawnień do przeniesienia na backend / Firestore rules:
- `users/{uid}`
  - create: tylko właściciel na własnym `uid`, z `status='pending'`.
  - read: właściciel lub admin.
  - update: admin (pełny) LUB właściciel bez zmiany pól `roles`, `status`, `email`, `uid`.
  - delete: tylko admin.
- `pools/{poolId}`: read publiczny; create/update/delete: admin lub organizer.
- `bookings/{bookingId}`: read: zalogowany; create: zalogowany; update/delete: właściciel rezerwacji, admin lub organizer.
- `allocations/{allocId}`: read: zalogowany; create/update/delete: właściciel (uid alokacji), admin lub organizer.
- `kayaks/{id}`: read publiczny; create/update/delete: admin lub organizer.

Reguła 24h **nie jest** egzekwowana po stronie reguł Firestore — jest walidowana wyłącznie w kliencie (patrz §5.2).

## 5. Widok `/terminy` — logika użytkownika

### 5.1 Lista terminów
- Kolekcja `pools`, sortowana `orderBy('date')`, subskrybowana live (`onSnapshot`).
- Dla każdego terminu renderowana jest „karta” z datą i lokalizacją.
- Wewnątrz karty: dla każdej godziny z `pool.hours` (H1, H2) renderowany jest `HourBlock`. Jeżeli `pool.saunaEnabled === true`, renderowany jest dodatkowy `HourBlock` dla `SAUNA` z ustalonym slotem **21:00–22:30**.

### 5.2 Zapis (`book`) — algorytm dokładny
Warunki wstępne (w tej kolejności):
1. Niezalogowany → alert „Zaloguj się przez Google” i przerwij.
2. `me.status !== 'active'` → alert „Twoje konto czeka na akceptację przez admina.” i przerwij.
3. Wylicz `startAt`: dla sauny `21:00` (stała), w przeciwnym razie `start` z `pool.hours.find(label===hour)`.
4. `within24h = Date.now() > startAt - 24h`.
5. Jeżeli `within24h` → `window.confirm(...)`:
   - dla sauny: „Zapis na saunę jest krócej niż 24h przed startem — nie będzie możliwości wypisania. Kontynuować?”
   - w przeciwnym razie: „Zapis jest krócej niż 24h przed startem — nie będzie możliwości wypisania. Kontynuować?”
   - Jeśli użytkownik anuluje — przerwij.

Transakcja (Firestore `runTransaction`):
1. Odczytaj `users/{uid}` — wymagane istnienie; `credits = Number(u.credits||0)`; jeżeli `credits <= 0` → błąd „Brak wykupionych godzin.”
2. Odczytaj `bookings/b_{poolId}_{hour}_{uid}`:
   - Jeżeli nie istnieje → utwórz z pełnym payloadem (§2.3), `type` = 'sauna' | 'training' | 'regular'.
   - Jeżeli istnieje i `status='active'` → błąd „Już masz aktywny zapis.”
   - Jeżeli istnieje i status ≠ 'active' → update: `{ status:'active', type, instructorUid, createdAt: serverTimestamp() }`.
3. `users/{uid}.credits = credits - 1`.

Po sukcesie: **żadnego alertu** (akcja odwracalna >24h). UI odświeży się przez subskrypcję.

### 5.3 Zapis z instruktorem (`training`)
- Osobny przycisk „Zapisz się z instruktorem (−1)” otwiera `InstructorPicker`, który listuje **aktywnych instruktorów zapisanych na tę godzinę** (bookings z `type='instructor'`, `status='active'`, dopasowane `poolId+hour`), pobierając ich `userName`.
- Po wyborze i „Potwierdź (−1)” wywoływana jest ta sama logika zapisu z `mode='training'` i `instructorUid`.

### 5.4 „Dodaj się jako instruktor” — tylko `roles.instructor`
- Osobna, dedykowana akcja (`addMeAsInstructor`), transakcyjnie:
  - Sprawdza czy nie ma już `active` zapisu tego użytkownika na tę godzinę z `type !== 'instructor'` (jeśli tak → błąd „Masz już aktywny zapis na tę godzinę.”).
  - Jeżeli booking nie istnieje: utwórz z `type='instructor'`, `userPublicRole='Instruktor'`, `instructorUid=null`, `kayakId=null`, pełen payload.
  - Jeżeli istnieje i był anulowany: `status='active', type='instructor', instructorUid=null, createdAt=now`.
- **Ta ścieżka NIE pobiera kredytu** i NIE dodaje kredytu.
- Bez alertu po sukcesie.

### 5.5 „Odbierz +1 za szkolenie” (instruktor)
Przycisk widoczny wyłącznie, gdy jednocześnie:
- `me.roles.instructor === true`,
- moja rezerwacja jest `active` i ma `type='instructor'`,
- `studentsCount > 0` (liczba `bookings` z `type='training', status='active', poolId, hour, instructorUid=me.uid` liczona live),
- `me.teachCredits['teach_{poolId}_{hour}']` **nie jest** `true` (nie odebrano wcześniej).

Akcja (transakcja):
- Odczytaj `users/{me.uid}`, sprawdź brak `teachCredits.teach_{...}=true` (błąd „Kredyt za tę godzinę już odebrany.”).
- `credits += 1`, `teachCredits.teach_{poolId}_{hour} = true`, `lastInstructorTeachAt = serverTimestamp`.
- Alert: `"+1 za szkolenie przyznany."`

### 5.6 Wypisanie się (`cancel`)
Warunki: aktualnie moja rezerwacja jest `active` **i** `Date.now() <= startAt - 24h` (czyli **wypis dozwolony tylko >24h przed startem**).

Sekwencja (bez pojedynczej transakcji — dwa kroki):
1. `updateDoc(bookings/{id}) { status:'cancelled', cancelledAt: serverTimestamp() }`.
2. Jeżeli `type !== 'instructor'`: refund +1 (transakcyjnie odczytaj `users/{uid}.credits`, `credits+1`, ustaw `lastRefundBookingId`, `lastRefundAt`).
3. Jeżeli był przypisany `kayakId` i **nie** był to `PRIVATE`: `deleteDoc(allocations/alloc_{poolId}_{hour}_{kayakId})` (błędy „połknięte”).

Alert (jeden z, w zależności od typu godziny):
- „Wypisano z sauny (+1).”
- „Wypisano (+1).”

Notatka: instruktor **nie dostaje** zwrotu +1 przy wypisaniu (bo nie płacił kredytem za wpis jako instruktor).

### 5.7 Kajaki — wybór i zmiana
Dostępne dla: `regular` i `training` (nie dla sauny, nie dla type='instructor').

Otwarcie pickera (`showKayakPicker`):
- Subskrybuj `kayaks` (live), filtruj `k.active !== false`, sortuj po `name || id`.
- Subskrybuj `allocations` gdzie `poolId==pool.id AND hour==hourLabel` — zbierz `takenKayakIds`.
- Do listy dostępnych bierz kajaki, które **nie są zajęte**, LUB kajak którego aktualnie posiadam.
- Do listy **zawsze doklej pozycję** `{ id: 'PRIVATE', name: 'Kajak prywatny' }` na końcu.
- W selekcie zajęte kajaki (poza własnym) mają suffix `" (zajęty)"`.

Potwierdzenie wyboru (`confirmKayak`):
- Jeżeli wybrano `PRIVATE`:
  - Jeżeli miałem wcześniej `kayakId` inny niż `PRIVATE` → usuń starą alokację.
  - `updateDoc(bookings/{id}) { kayakId: 'PRIVATE' }`.
  - Bez alertu (odwracalne).
- W przeciwnym razie (kajak z inwentarza) — transakcja:
  1. Odczytaj booking; wymuś: istnieje, `uid==me`, `status='active'`.
  2. Odczytaj `allocations/alloc_{poolId}_{hour}_{chosenKayak}` — jeżeli istnieje → błąd „Ten kajak jest już zajęty dla tej godziny.”
  3. Jeżeli miałem stary `kayakId` (i nie było to `PRIVATE`): usuń jego alokację w tej samej transakcji.
  4. Ustaw nową alokację (patrz §2.5) i `updateDoc(bookings/{id}) { kayakId: chosenKayak }`.
- Bez alertu po sukcesie.

Wyświetlenie nazwy kajaka:
- Dla `PRIVATE` → „Kajak prywatny”.
- W przeciwnym razie subskrybuj `kayaks/{kayakId}` i pokaż `name` (fallback: `kayakId`).

### 5.8 Lista zapisanych (`AttendeesList`) — publiczna sekcja per godzina
Wejście: `poolId`, `hour`. Subskrypcja: `bookings` gdzie `poolId+hour+status='active'`. Podział na cztery sekcje (renderowane tylko gdy niepuste):

1. **„Pary: Uczestnik — Instruktor”** — bookings `type='training'` z ustawionym `instructorUid`. Nazwę instruktora bierz z bookings `type='instructor'` po `uid==instructorUid`. Sort: po `userName` uczestnika.
2. **„Instruktorzy dostępni”** — bookings `type='instructor'`, których `uid` **nie występuje** wśród `instructorUid` sparowanych `training`ów. Sort: po `userName`.
3. **„Uczestnicy”** — `type='regular'` + `type='training'` **bez** przypisanego instruktora. Sort: po `userName`.
4. **„Sauna”** — `type='sauna'`. Sort: po `userName`. Element z suffixem „(sauna)”.

Jeżeli wszystkie sekcje są puste — nic nie renderuj.

## 6. Widok `/admin/terminy`

### 6.1 Lista i sortowanie
Live subskrypcja `pools orderBy('date')`. Każdy termin wyświetla `date`, `location`, listę godzin w formacie `H1:21:00–21:45 · H2:21:45–22:30` + `· sauna 21:00–22:30` gdy włączona.

### 6.2 Formularz dodania terminu
Pola: `date` (`<input type="date">`), `location` (start z DEFAULT_LOCATION, edytowalne), `h1s/h1e/h2s/h2e` (`<input type="time">`), `capacity` (int), `trainingSlots` (int), `sauna` (checkbox).
Walidacja klienta: wymagane `date` i `location`, w przeciwnym razie alert „Uzupełnij datę i lokalizację.”
Zapis: `addDoc('pools', { date, location, hours:[H1,H2], saunaEnabled, createdAt })`. Po dodaniu — reset formularza do wartości domyślnych i alert „Dodano termin.”

### 6.3 Usuwanie terminu
Confirm: `"Usunąć termin {date} – {location}? Zapisanym zostanie zwrócona 1 godzinka."`.

Algorytm (per hour ∈ [H1, H2, SAUNA]):
1. Pobierz aktywne bookings dla `poolId+hour+status='active'`.
2. Dla każdego booking utwórz `writeBatch`:
   - `bookings/{id}.status = 'cancelled_admin'`, `cancelledAt = serverTimestamp`.
   - Jeżeli `type !== 'instructor'` → `users/{b.uid}.credits += 1` (przez `increment(1)`).
   - Jeżeli `b.kayakId && b.kayakId !== 'PRIVATE'` → usuń `allocations/alloc_{poolId}_{hour}_{b.kayakId}`.
   - `batch.commit()`.
3. Po wszystkim: `deleteDoc('pools/{poolId}')`.
4. Alert „Termin usunięty. Zwroty zostały przyznane.”

Uwaga: użycie `increment(1)` zamiast pełnej transakcji jest świadome (nie wymaga read-modify-write).

## 7. Widok `/admin/uzytkownicy`

Zakładki i wyszukiwarka nad listą.

### 7.1 Zakładki
`pending | active | archived | all`. Domyślnie `pending`.
- `all`: `query(users, orderBy('createdAt','desc'))`.
- pozostałe: `query(users, where('status','==', tab))` (bez orderBy — sort **lokalny** po `createdAt` malejąco; celowo unikamy złożonych indeksów).

### 7.2 Wyszukiwarka (lokalna, po pobraniu)
Wpisany tekst filtruje `displayName`, `email`, `id (uid)` case-insensitive.

### 7.3 Akcje per użytkownik
- **Status**: przyciski „Aktywuj”, „Archiwizuj”, „Ustaw »oczekujący«”. Przycisk aktualnego statusu jest ukryty. Update: `{ status, statusUpdatedAt: serverTimestamp }`.
- **Role**: trzy checkboxy `admin`, `organizer`, `instructor`. Update: `{ 'roles.<key>': val, rolesUpdatedAt: serverTimestamp }`.
- **Credits**:
  - Przyciski `+1`, `−1` — `updateDoc { credits: increment(±1), creditsPatchedAt }`.
  - Pole liczbowe + „Ustaw na” — walidacja `NaN` z alertem „Podaj liczbę.”, następnie transakcyjny odczyt-zapis: `credits = target, creditsPatchedAt`.

### 7.4 UI info per użytkownik
Wyświetlaj: `displayName || email || uid`, `email` (lub „brak e-maila”), `status`, `uid`, aktualne `credits`, checkboxy ról.

## 8. Widok `/admin/kajaki`

Live subskrypcja `kayaks`. Sort: aktywne pierwsze, potem alfabetycznie po `name`.

Akcje:
- **Dodaj kajak** — pola `name` (wymagane; alert „Podaj nazwę kajaka.” gdy puste), `note` (opcjonalne). Zapis: `{ name, note, active:true, createdAt }`.
- **Toggle active** — update pola `active`.
- **Rename** — na blur inputa z nazwą, jeżeli nowa nazwa niepusta.
- **Update note** — na blur inputa z notatką.
- **Usuń** — confirm „Usunąć kajak? (nie usuwa przydziałów historycznych)”, następnie `deleteDoc`.

## 9. Elementy istniejące w kodzie, lecz **niewpięte** (do rozważenia)

Poniższe komponenty istnieją, lecz nie są zarejestrowane w routingu obecnej wersji. Zdecyduj świadomie, czy odtworzyć je w nowym projekcie.

### 9.1 `Moje` — „Moje zapisy”

- Zawiera pomocniczą funkcję z **retry** dla refundu (5 prób co 1000 ms) — do użycia, jeżeli reguły serwerowe wymagają, by refund „zobaczył” już zapisane `cancelledAt`.

### 9.2 `Kup` — informacje o pakietach (płatność przelewem)
Statyczna strona z informacjami:
- Odbiorca: **Radosław Orzlowski**
- Nr konta: **13160014621861303220000001**
- Pakiety:
  - Members 6 wejść – 168 zł
  - Others 4 wejścia – 155 zł
  - Members 2 wejścia – 60 zł
- W tytule przelewu należy podać nazwę użytkownika z aplikacji (jeśli różna od imienia/nazwiska).

### 9.3 Cloud Functions (`functions/src/index.ts`)
W repo istnieją dwie funkcje `onCall` w regionie **`europe-central2`**, **nieużywane** przez obecny klient (klient robi te operacje bezpośrednio przez Firestore + transakcje):
- `createBooking({ poolId, hour, type })` — analogiczna logika tworzenia rezerwacji + jeżeli `active.size >= capacity`, tworzy dokument w **`waitlists`** (`{ poolId, hour, uid, type, createdAt }`) zamiast rezerwacji.
- `cancelOrMoveBooking({ bookingId })` — ustawia `status='cancelled', cancelReason:'user'`; **nie egzekwuje** reguły 24h.

Jeżeli w nowym projekcie chcesz mieć **listę oczekujących** (waitlist) — to jedyny ślad tej funkcjonalności w bazie kodu. W kliencie **nie ma** żadnej integracji z waitlists (brak widoku, brak promocji z waitlisty).

## 10. Reguły biznesowe — podsumowanie do wdrożenia

Rzeczy, których nie wolno pominąć w reimplementacji:

1. **Jedna rezerwacja na (user × pool × hour)** — enforcowana kluczem `b_{pool}_{hour}_{uid}`.
2. **Jeden kajak na (pool × hour)** — enforcowany kluczem `alloc_{pool}_{hour}_{kayak}` i wewnątrz transakcji zmiany kajaka.
3. **Credits pobierane tylko przy `regular/training/sauna`, nigdy przy `instructor`.**
4. **Wypis dozwolony wyłącznie >24h przed `startAt`** (weryfikowane w kliencie, konsekwentnie w obu ścieżkach: Terminy i Moje).
5. **Zwrot +1 przy wypisie tylko dla `regular/training/sauna`**, nigdy dla `instructor`.
6. **Zapis <24h wymaga potwierdzenia (`confirm`) z jasnym komunikatem o braku możliwości wypisu.** Zapis >24h nie pokazuje żadnego alertu ani po zapisie, ani po zmianie kajaka (akcje odwracalne — feedback ma dawać UI live).
7. **Instruktor odbiera +1 za szkolenie wyłącznie raz na (pool × hour)** — rejestrowane w `users.teachCredits['teach_{poolId}_{hour}']=true`. Warunki widoczności przycisku: rola, aktywna rezerwacja instructor, ≥1 kursant, brak wcześniejszego odebrania.
8. **Admin usuwający termin zwraca +1 wszystkim płatnym typom**, kasuje aktywne bookings do `cancelled_admin`, sprząta alokacje inwentarzowych kajaków, następnie kasuje sam termin.
9. **Nowy użytkownik startuje z `status='pending'` i musi zostać zaakceptowany przez admina** zanim się zapisze; klient pokazuje baner i blokuje zapis.
10. **Etykieta publiczna użytkownika (`userPublicRole`) wyliczana jest wg ustalonego priorytetu** (§3.3) w momencie tworzenia rezerwacji i zapisywana w niej (nie liczona live przy renderze list uczestników).
11. **„Kajak prywatny” (`PRIVATE`) jest specjalny** — nie tworzy alokacji, nie blokuje puli, nie usuwa się przy anulowaniu; użyty tylko jako etykieta w rezerwacji.
12. **Wszystkie listy w UI są live** (`onSnapshot`) — użytkownik widzi zajęte kajaki, dostępnych instruktorów, i skład grupy w czasie rzeczywistym.

## 11. UX — konwencje komunikatów

- Sukces akcji **odwracalnej** (>24h zapis, zmiana kajaka, dodanie się jako instruktor) → **żadnego alertu**.
- Wypis → alert („Wypisano (+1).” / „Wypisano z sauny (+1).”) — ważny feedback.
- Odebranie +1 za szkolenie → alert („+1 za szkolenie przyznany.”).
- Błąd → `alert(err.message || fallback)`; kod loguje też do `console.error`.
- Zapis <24h → `window.confirm(...)` przed akcją.
- Usunięcie terminu / kajaka → `window.confirm(...)` przed akcją.
- Wszystkie przyciski akcji wyłączają się i pokazują tekst „Zapisywanie…”, „Wypisywanie…”, „Dodawanie…”, „Ustawianie…”, „Przetwarzam…” w trakcie operacji.

## 12. Stos technologiczny (obecny; do zaadaptowania w nowym projekcie)

- Frontend: React 18 + Vite 5 + TypeScript + `react-router-dom` v6.
- Backend / DB / Auth: Firebase (Auth Google, Firestore, opcjonalnie Cloud Functions w regionie `europe-central2`).
- Konfiguracja Firebase przez zmienne środowiskowe Vite: `VITE_API_KEY`, `VITE_AUTH_DOMAIN`, `VITE_PROJECT_ID`, `VITE_STORAGE_BUCKET`, `VITE_MESSAGING_SENDER_ID`, `VITE_APP_ID`.
- Zależności runtime (przenośne): `firebase`, `react`, `react-dom`, `react-router-dom`.

W nowym projekcie możesz zastąpić Firestore innym backendem, o ile zachowasz:
- Idempotencję ID rezerwacji i alokacji (patrz §2.3, §2.5).
- Serwerową atomowość przy: (a) zapisie z odjęciem kredytu, (b) zmianie kajaka z jednoczesną walidacją zajętości, (c) refundzie, (d) rezerwacji przez instruktora bez kredytu.
- Live-updates list (websockety / SSE / polling).
- Ograniczenia dostępu równoważne §3.4.
